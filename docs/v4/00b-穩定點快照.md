# v4 穩定點

> 2026-08-12 建立。基準是本文件所在的這個 commit——程式碼側停在 `20dce92`
> （六屬性面板展開箭頭），再加上第五節列出的測試修正。

這份文件記錄 v4 的**已驗證穩定基準**：現在站在哪裡、安全網真正守得住什麼、
量到的數字長什麼樣、哪裡還是空的。後續 v4 文件都以這份為基準；任何一項描述
與程式碼不符，是這份文件要改，不是程式碼要遷就它。

寫這份文件的理由很實際：v4 一口氣改掉賽制、種子語義與養成模型三件事，
散在 `CHANGELOG` 與 `WORKLOG` 的敘述已經追不上「現在到底是什麼樣子」。
穩定點就是把「現在」釘死一次，讓下一步有東西可以 diff。

## 二、結構上守住的東西

這些是 v4 的承重牆。改動如果會破壞其中任何一條，那不是「在穩定點上往前走」，
是要另外開一個穩定點。

**① 依賴方向單向**：`data ← kernel ← phases ← engine ← ui`。
`engine/` 不 import `ui/`、不碰 `document`，所以整段生涯可以在 Node 裡跑完——
測試能存在，靠的就是這條。

**② 階段只匯出兩個東西**：`export const kind` 與 `export function* run(g, phase)`。
階段不 import `game.js`，沒有循環依賴。**新增一個賽事＝寫一個檔、註冊一行、年曆加一列。**

**③ 一年有哪些賽事是資料**：`data/formats/calendar.js` 一張表。賽段拿 10／20／30，
任何「插在第 n 賽段之後」的賽事取 `10n+5` 就落在正確的縫裡。MSI 從年末歸位到賽季
中段，改的是一列資料。

**④ 賽區是實體**：一個賽區一個檔（`data/regions/*.js`），席位數、賽段數、外援名額、
隊名都住在同一個檔。新增一個賽區＝1 改 1 新。

**⑤ 特質效果是資料**：`data/traits.js`／`epics.js` 自己宣告效果，消費端只問
`kernel/modifiers.js` 的 `bonus`／`factor`／`floorOf`／`capOf`／`flag`。四種運算刻意
不合成單一 `apply()`——不同消費點的組合順序不同，統一會把順序藏起來。

**⑥ 兩條亂數流**：出生流（種子決定天賦）與人生流（每局隨機抽）。
引擎本身仍是 `(出生種子, 人生種子, 選擇)` 的確定性函式——隨機的是「誰來決定人生種子」，
不是引擎。存檔續玩與黃金種子回歸都建立在這條上。

**⑦ 兩層養成**：玩家只經營六屬性；十三項技能是導出值，唯讀。技能刻意只掛 2～4 個
屬性——沾滿五、六個屬性會讓五路的權重折疊後長得一樣，位置身分被平均掉。

## 三、安全網覆蓋到哪裡

`tests/run.mjs` 自動掃描四個目錄，加 suite 不必改 runner。

| 分區 | 檢查數 | 內容 |
|---|---|---|
| `kernel/` | 5300 | BO 系列與種子序、小組賽與 Swiss、特質合成、版本落差方向、心理值揭露界線、扮演卡與心理維度的界線、聯賽階梯與分區名稱 |
| `phases/` | 1184 | 業餘起點與挖角時機、先發板凳與傷勢缺席、自由市場與挖角門檻、轉會窗口與外援名額 |
| `history/` | 350 | 史實斷言：2020 無 MSI、2022 不得 Swiss、2025 不得用冠軍點數、席位數逐年、二隊隊名不得時代錯置、解散與簽約名單過濾 |
| `regression/` | 2101 | 160 段生涯冒煙與不變式、種子界線、黃金種子快照、一段生涯的年表 |

**黃金種子快照**（`regression/golden.json`）錄下 160 段生涯的 state 雜湊與可讀摘要。
純重構必須逐位元一致；有意的賽制改動用 `npm run test:golden` 重新 baseline，
並在 commit 訊息說明差異來源。這是目前唯一擋得住「無意間改動平衡」的機制。

冒煙矩陣＝16 組種子 × 五路 × 兩種加點打法（focus 集中／spread 平均）＝160 段完整生涯。
`smoke.mjs` 跑完把樣本放進 `shared`，後面的 suite 直接取用，所以整份測試只跑一次矩陣。

### 守的不變式

屬性值 1..cap、版本落差 0..10、英雄池 ≤8、合約年限 ≥0、年齡 ≤41、薪資 ≥0、
生涯必須結束且必須有退役原因。

|---|---|---|

| 平均職業年資 | 14.4 季 | 12.7 季 |
| 平均榮譽數 | 12.1 項 | 9.9 項 |
| 人均世界賽冠軍 | 0.05 座 | 0.03 座 |
| 人均 MSI 冠軍 | 0.19 座 | 0.24 座 |
| 平均退役年齡 | 36.2 | 36.0 |

生涯評價分布（每種打法各 80 段）：

| 等第 | 老手 | 新手 |
|---|---|---|
| 傳奇 | 5 | 1 |
| 歷史級選手 | 11 | 13 |
| 優秀職業選手 | 27 | 32 |
| 稱職選手 | 33 | 33 |
| 邊緣選手 | 4 | 1 |

退役年份落在 2030–2036。

> **加點差距只有 2.3 點 OVR，這是結構性的。** 九素質時代平均分配是災難，但那個懲罰
> 有一半來自每路有 2/9 的素質權重為 0——平均分配等於丟掉兩成的點。六屬性對每一路
> 都有份量，加上權重和固定為 1、成本階梯是凸的，平均分配拿到的就是平均值。
> 要再拉開只能重新引進「對某些位置無用的屬性」，那正是六屬性改制要拿掉的東西。
> 冒煙測試因此換了指標：守「傳奇仍罕見」與「巔峰 OVR 差距 ≥1.5」，而不是舊的
> 「新手不得出現傳奇」。

## 五、建立這個穩定點時修掉的東西

穩定點不是宣告現狀正確，是把現狀對過一遍。這一輪對出來的：

**① `determinism.mjs` 有半條檢查是空的。** 「同種子＝同天賦」比對的欄位寫
`ability: s.ability`，但六屬性改制時 `state.ability` 已改名為 `state.attr`——
兩邊都是 `undefined`，屬性那一半從此沒有被比對到。已改為 `attr: s.attr`。

**② 同一支 suite 裡有一條恆真檢查。** `birthOf(...) !== undefined` 永遠成立。
改成比對潛力天花板：`potential` 是出生固定、整段人生只讀不寫的欄位，
拿它驗「天賦沒被人生改寫」才有意義（屬性本身會隨加點成長，不能拿完賽的 state 比）。

**③ 文件指向不存在的檔案。** `README`／`ESPORT-DESIGN` 還寫 `node tests/headless.mjs`
（v4 已拆成 `tests/run.mjs`）；`ESPORT-DESIGN` 的規則對應表整張表指向
`world.js`／`abilities.js`／`international.js`／`team.js` 這些已經不存在的檔案；
`ARCHITECTURE` 的目錄樹還列著 `data/abilities.js`／`engine/abilities.js`。全部重對。

**④ 文件還在描述 v3 的賽制。** `ESPORT-DESIGN` 與 `WIKI` 的國際賽章節仍寫著
「MSI：OVR≥52 被徵召、可婉拒、國際賽消耗使受傷風險 +10%」——那是 v4 整套拆掉的
國家隊模型。已改寫為俱樂部賽事、種子序門票、地區資格賽與 BO 系列。

**⑤ 其他對不上的小處**：評價表寫「歷史級球星」（實際是「歷史級選手」）、
生涯評分公式漏了勝差的 `max(-200, …)` 地板、`README` 仍寫「同種子＋同選擇＝同一段
人生」（v4 的種子只決定天賦）、`PRODUCT`／`DESIGN` 沒有屬性列與技能列的區別。

## 六、已知缺口（不阻塞，但別假裝不存在）

- **UI 沒有自動測試。** 8935 項全在引擎層。面板、加點列、抽屜、分享圖只有人工驗證。
  引擎測得再密，`src/ui/` 出的錯一項都擋不到。
- **`TEAMS_OVERSEAS` 是單一現代快照。** 2012 年也會看到後來才成立的隊伍。
  主場賽區的隊名有逐年推導，海外沒有。
- **英雄池與版本 Meta 採現代快照**，不隨時代回溯英雄清單。
- **海外賽區沒有歷史解散事件**，`disband.js` 目前以主場賽區為主。
- **能力系隱藏素質仍偏難**：`disc`／`leader`／`laneking`／`macroG` 的解鎖率極低，
  瓶頸在抽卡頻率與素質本身的額外門檻，v4 沒有動它們。
- **黃金種子快照擋得住「結果變了」，擋不住「結果變得更差」。** 它只比對一致性，
  平衡好壞仍然要靠分布檢查與人的判斷。
- **`WORKLOG` 記過但沒解的事**：若想找回加點的份量，方向應該是讓 OVR 對「尖峰」
  有非線性回報，而不是加回死屬性。

## 七、怎麼算「還在這個穩定點上」

往前走的時候，用這三條自檢：

1. **`npm test` 全綠**，而且檢查數只增不減——減少通常代表某條檢查被改成恆真或
   比對到 `undefined`（第五節①②就是這樣長出來的）。
2. **黃金種子快照**：純重構必須逐位元一致。有差異就必須說得出差異來源，
   說不出來就不是重構。
3. **文件與程式碼對得上**：改了賽制或改了檔名，同一個 commit 要把 `ARCHITECTURE`
   的目錄樹、`ESPORT-DESIGN` 的規則對應表、`WIKI` 的攻略一起帶到。
   這三處是最容易變成考古層的地方。

承重牆（第二節）要動的話，先開下一個穩定點，不要就地改。
