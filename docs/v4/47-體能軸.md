建議模型：Sonnet 5（`claude-sonnet-5`）
理由：兩個係數 + 兩個消費點，形狀都照抄既有的 `vitCoef`，落點與量級本站已寫定。
唯一需要判斷的是「選單顯示要跟著折扣走」這條，說明書已點名。雪球風險的量測與

## 為什麼做這件事

`vit`（體能）目前只有**一個**消費者：`stamina.js:189` 的 `vitCoef`，掛在恢復量上，
60 為中性、滿值 +20%。而 S10 的十二技能表把 `vit` 的 OVR 權重**全部歸零**（體力被
抽出來當資源了）——`stamina.js` 的檔頭註解自己寫著這件事：「如果體力再與 `vit` 無關，
這個屬性就完全沒有消費者，加點加到它等於丟進水裡。」

恢復量那一項是刻意做小的（「它是體質差異，不是另一條成長線」），結果 `vit` 至今仍是
六屬性裡最沒有存在感的一個。S46 之後這件事更尖銳：`vit` 是**健身房的主屬性**，
如果它依然只影響恢復量，健身房就會是六個選項裡明顯最弱的一格。

本站給 `vit` 兩個新效果，讓它成為一條**投資型**的軸——不推高評價，但讓之後每個月的
訓練都更便宜、更安全。

## 範圍

### 要做

**1. 體能越高，訓練消耗的體力越少**

在 `src/engine/stamina.js` 新增，形狀刻意寫成 `vitCoef` 的**鏡像**（同中點 60、
同斜率 0.005、同 ±20% 上下界）——一個屬性對「回得多」與「耗得少」的影響量級應該對稱，
兩條曲線放在一起要一眼看得出是同一件事的兩面：

```js
/** 體能對訓練消耗的折扣（`vitCoef` 的鏡像）。60 中性、100 打八折、20 加兩成 */
export function vitCostCoef(state) {
  return clamp(1 - ((state.attr?.vit ?? 60) - 60) * 0.005, 0.8, 1.2);
}

/** 一次訓練實扣的體力。整數化在這裡做一次，讓選單顯示與實際扣除是同一個數 */
export function trainCost(state, cost) {
  return Math.round(cost * vitCostCoef(state));
}
```

- `resolveTraining` 改成 `consume(state, trainCost(state, activity.cost))`。
- **不動 `consume` 本身**——它同時被 `MATCH_MONTH_COST`（常規賽月）與
  `SERIES_GAME_COST`（BO 每局）用著。折扣只掛訓練：賽季的體力經濟是另一條線，
  本站不碰，動它會連帶改到 §11.1 的手感係數分布。
- ⚠ **`activityInfo` 的 `staminaDelta` 必須改讀 `trainCost`**。否則選單印的
  `體力 −30` 會跟實際扣的 −24 對不上——**選單不能說謊**。`trainCost` 已經 round 過，
  顯示與效果因此同源（這是把 round 放進 `trainCost` 而不是放在顯示端的唯一理由）。

**2. 體能越高，受傷機率越低**

`src/engine/progression.js` 的 `injuryProbability`，接在既有的 `injuryMul` 之後、
`capOf` 之前：

```js
p *= injuryMul(staminaOf(state));
p *= vitInjuryCoef(state);        // 體能：這副身體耐不耐操
p = capOf(state, 'injuryRate', p);
```

```js
/** 體能對受傷機率的體質修正。100 → ×0.76、20 → ×1.24 */
export function vitInjuryCoef(state) {
  return clamp(1 - ((state.attr?.vit ?? 60) - 60) * 0.006, 0.75, 1.25);
}
```

用**乘法**而非加法，理由與該函式既有的註解同一條：年齡是「身體本來的脆弱度」、
體力是「今天有沒有在硬撐」、體能是「這副身體耐不耐操」——三者相乘才有交互作用
（33 歲 ＋ 透支 ＋ 低體能才是真的危險，任兩項單獨都不是）。

放在 `capOf` **之前**是刻意的（沿用既有註解的理由）：帶受傷率上限那類特質的人，
體能再差也還是有天花板。結尾的 `clamp(p, 3, 95)` 不動——體能再高也不會免疫，
那是 `injuryImmune` 旗標的地盤。

### 不要做

- **不做校準**。本站會讓可訓練的月份變多（成本下降），但 S46 的權重集中是反向的力
  ——兩股力的淨值只能實測，量測與收斂在 S50。這裡不要動 `TRAIN_YIELD`、
  不要動 `MONTHLY_RECOVER`。
- **不動 `consume` 的其他呼叫端**（比賽消耗維持原樣）。
- **不動 `vitCoef`（恢復量）的係數**——只更新它的檔頭註解。
- **不碰教練**（S49 的 `trainCostMul` 會疊在同一個 `trainCost` 上，但那是下一站）。
- **內容編輯器不必動**：本站只動引擎內部係數，沒有新增任何可編欄位、可選值或效果鍵。
  這句話要寫進交接筆記，否則 S49 會重查一遍。

## 規則與不變式

- **選單不能說謊**：`trainingMenu` 印的 `staminaDelta` 與 `resolveTraining` 實際扣掉的
  量必須逐字相同。這是本站唯一的新不變式，也是最容易漏的一處。
- **比賽消耗不吃折扣**：`MATCH_MONTH_COST` 與 `SERIES_GAME_COST` 的路徑不經 `trainCost`。
- **受傷機率的邊界不動**：`clamp(p, 3, 95)` 與 `injuryImmune` 短路的行為與改前一致。
- **兩個係數都有 clamp**，`state.attr` 缺失時退回中性值 60（沿用 `vitCoef` 的
  `?? 60` 寫法，舊存檔不得傳染 `NaN`）。

### ⚠ 偏離說明書字面的一處（rest／rehab 的顯示）

說明書寫「`activityInfo` 的 `staminaDelta` 必須改讀 `trainCost`」。但 `rest`／`rehab`
的 `cost` 是**負數**（走 `recover`，不吃 `consume`）——鏡像 `vitCostCoef` 套上負數
會讓顯示方向顛倒（高 vit 顯示恢復更少、實際恢復更多），比改前的「基準價 +50」更謊。
所以恢復活動的顯示改讀 `recover` 的實際量：`Math.round(-cost × vitCoef(state))`，
消耗活動照說明書走 `-trainCost`。「選單不能說謊」不變式因此對兩側都成立。

### 給 S49（教練六選一）

- `trainCost(state, cost)` 現在是「一次訓練實扣」的唯一介面——教練的 `trainCostMul`
  疊進來時**乘積順序**：`Math.round(cost × vitCostCoef × trainCostMul)`。把折扣與教練
  修正的順序固定並寫進檔頭註解，不要讓 round 的時點漂移（round 只能做一次、在最後）。
- ⚠ `trainCost` 的語意是「正成本＝消耗」：`rest`／`rehab` 的負成本不走它（走
  `recover` 分支），疊 `trainCostMul` 時別拿負數呼叫。
- 內容編輯器**不必動**：本站只動引擎內部係數，沒有新增任何可編欄位、可選值或效果鍵
