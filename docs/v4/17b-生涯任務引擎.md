# S17b · 生涯任務引擎（傳說／路線事件卡）

狀態：已完成（2026-08-15）
前置：S17 S17a
預估：1 session
推理難度：高
建議模型：Opus 5（`claude-opus-5`）
理由：這是 V4.1 唯一的新子系統，而且它握著**傳說特質的唯一發放口**——判斷成本高，
因為 S07 的兩條傳奇不變式全部經過它。設計上要決定的東西不少（期限怎麼算、素材何時
消耗、失敗怎麼降階），而每一個決定都會移動持有率。


> ⚠ **v4.2 增訂**（§12.3）：多了三條規則，全部影響狀態機的形狀——
> （一）**素材失效即失敗**：進行中的任務若素材被其他已達成的任務吃掉，立即判未達成、
> 永久失敗、降階為生涯標籤；（二）**失敗通知不得靜默**，要講清楚是哪張卡吃掉哪個素材
> （所以帳本要記得下消耗的時間點與來源，S17a 的查詢函式要能回答）；
> （三）**同結算點按開卡時間排序**，先開先吃。
> 校準時**要把「失敗」也算進持有率的分母**，否則會誤判門檻太鬆。

> ⚠ **v4.3 增訂**（§12.3）：原第三條約束「條件必須由看得見的狀態組成、隱藏心理不准
> 當條件」**已廢止**——特質編輯器的觸發條件（§14.7）與生涯任務卡的條件式**可讀隱藏
> 心理六維**（「comp 跌破某值」是合法設計）。下方原本的「不准把隱藏心理六維放進
> 謂詞表」禁令撤銷；謂詞表可擴充心理謂詞（讀 `state.mental`，經 `ledger.js`）。
> 另 §14.2 那 20 組固定素材條件作廢，傳說觸發條件由 S18a 的特質編輯器重新定義——
> 本引擎只認「條件式」，不認任何固定形狀。

## 為什麼做這件事

V4 §12.3 新增了**生涯任務卡**。它與 S17 做的 §12.1 觸發引擎是兩回事：

| | §12.1 事件卡（S17） | §12.3 生涯任務卡（本站） |
| --- | --- | --- |
| 生命週期 | 當月結算完就結束 | **跨回合存活**，直到達成或逾期 |
| 觸發 | 每月抽 1～2 張 | 條件命中即開，**不佔每月配額** |
| 結果 | 屬性／體力／心理／特質線索 | 傳說特質，或史詩特質＋生涯標籤 |
| 玩家可見 | 選項與敘事 | **進度與期限都可見** |

而且它是傳說特質的**唯一**來源（§13.4）——v4.1 把「持有史詩＋稀有即自動合成傳說」
整個拿掉了，改成那組素材只是任務卡的**觸發條件**。所以這一站不做，S19b 的 20 個傳說
特質就沒有地方發出去。

## 範圍

### 要做

**必讀規格**：V4 §12.3（任務卡結構與規則）、§14.2（底線門檻）、§14.3（5 條 `route`
的條件）、§14.7（特質編輯器——傳說觸發條件由此定義）、§13.4（傳說只有一個來源）。

**1. `src/engine/quests.js`（新檔）：狀態機**

```
每月（或每個結算點）跑一次：
1. 掃未觸發的卡 → 觸發條件命中 → 開卡，推進 state.quests
2. 掃進行中的卡 → 檢核達成目標 → 達成則結算「達成結果」
3. 掃進行中的卡 → 期限已過且未達成 → 結算「未達成結果」，標記永久失敗
```

`state.quests` 的形狀：

```js
quests: {
  active: [],   // [{id, openedYear, openedMonth, deadline, progress}]
  done: [],     // [{id, result: 'achieved' | 'failed', year}]
}
```

純函式，吃 `state` ＋ 卡表 ＋ `rng`，回傳要套用的變更。**不做呈現**——呈現接在
`phases/shared.js`，與 S17 的切分方式一致（觸發是規則可測，敘事難測）。

**2. 三個必須先定案的規則**

這三條是這一站真正的判斷成本所在，交接筆記要寫下選了哪個、為什麼：

| 決定 | 建議 | 理由 |
| --- | --- | --- |
| 素材何時消耗 | **達成時才消耗** | §14.1 已寫。開卡就吃素材的話，逾期失敗等於白虧兩個特質，玩家會學會不開卡——那是防農檢驗擋的那種反玩法 |
| 期限怎麼計 | 以**賽季**為單位，不是月 | §12.3 的例子就是「2 個賽季內」。月為單位會讓期限受 S14 的月推進節奏影響，難校準 |
| 失敗怎麼降階 | `legend` 失敗 → 生涯標籤；`route` 失敗 → 生涯標籤 | §12.3 表。**不要讓 `legend` 失敗掉成史詩**——那會讓史詩持有率被任務卡灌水，破壞 §14.2 的驗收線 |

**3. 條件式求值器（`legend` 的觸發條件不是固定欄位）**

⚠ **這是這一站最容易做錯的地方。** V4 §12.3 明文：觸發條件是**條件式**，
「1 史詩 ＋ 1 稀有」只是 §14.2 那 20 張卡目前寫成的樣子，**不是 schema 的形狀，
更不准寫死進引擎**。做成兩個固定欄位（`needEpic` / `needRare`）的話，後續想寫
「兩個稀有」「賽事成績 ＋ 一個稀有」「純軌跡不吃素材」的傳說就全部卡死——
而那正是玩家能從電競邏輯推敲取得條件的來源。

要做的是一個小求值器：吃條件式 ＋ `state`，回傳布林。

```js
// 條件式是資料，不是程式碼。求值器認得的節點：
['and', ...]  ['or', ...]  ['not', x]
['has', 階, 鍵]        ['hasCount', 階, n]
['stat', 查詢函式名, 比較子, 值]
```

謂詞的最小集合見 V4 §12.3 的表（特質持有／賽事戰績／生涯軌跡／個人數據／狀態量／
時代賽區）。**每一個謂詞都轉呼叫 S17a 的 `engine/ledger.js`**，不直接翻 `state` 的
原始欄位——加新謂詞就是加一個查詢函式，不動求值器。

達成目標用**同一套語法**（§12.3 的 schema 兩欄都是條件式），不要寫兩套。

**兩條禁止**：

- **不准讓條件式有副作用**。求值是純函式，跑幾次結果都一樣

> v4.3 起隱藏心理六維**可以**進謂詞表（§12.3 第三條約束已廢止）——但要經
> `engine/ledger.js` 的查詢函式讀，不直接翻 `state.mental` 原始欄位（見上）。

**4. 底線門檻寫在引擎層**

V4 §14.2：「生涯至少一次國際賽四強以上」是**所有 `legend` 卡的共同觸發條件**。
在求值器裡一律 AND 上去，**不要逐卡複製** 20 遍——複製 20 遍就等著漏一張。

這一條**不在設計自由度裡**：條件式怎麼組是設計自由，但底線門檻是傳說持有率 ≤50% 的
守門員，任何一張 `legend` 卡都繞不過。

**5. 生涯標籤**

`state.labels: []`。標籤不是特質：**沒有 `effects`，不進合成樹，不吃 `modifiers`**。
它只是給 §15.5 傳記與結算畫面讀的字串。這條界線要守住，否則標籤會變成第五階特質。

**6. UI：進度可見**

§12.3 明文要求進度與期限可見。接在 `src/ui/panel.js`——最小可用即可（卡名＋目標＋
剩餘賽季數），漂亮留給 S21。

### 不要做

- **不要寫任務卡的內容**（S18 寫 20 張 `legend` ＋ 5 張 `route`）。這一站只做引擎，
  卡表可以先放 2～3 張假卡當測試素材
- **不要動 S17 的 §12.1 觸發引擎**。兩者共存，任務卡不佔每月配額
- **不要讓標籤有數值效果**
- **不要把觸發條件做成固定欄位**（`needEpic`／`needRare` 那種）。它是條件式，見上
- **不要放寬 S07 的傳奇不變式**
- 不要碰 `positionPower` 的乘法項

## 規則與不變式

- S07 不變式全綠，**特別盯「傳奇要罕見」與「持有傳說特質的生涯不得超過一半」**——
  這一站是傳說的唯一發放口，破了就是這裡破的
- 同一張卡生涯內最多觸發一次（達成或失敗都不再開）
- 逾期失敗後素材**未被消耗**，可以走別的組合
- `labels` 不影響任何數值：掃一遍 `kernel/modifiers.js`，確認它讀不到 `labels`

單元測試至少要蓋到：開卡 → 達成、開卡 → 逾期、素材在達成時才消耗、同時開多張、
底線門檻擋住未打過國際賽四強的生涯。

**求值器另外要蓋到三種形狀都通得過**——「一史詩＋一稀有」「兩個稀有」「賽事成績＋
一個稀有」。這三個測試存在的理由就是防止有人把條件寫回固定欄位：形狀被鎖死的話，
第二與第三個會紅。

### 定案（§12.3 三個「判斷成本」）

1. **素材何時消耗**：達成時才消耗（§14.1 已寫死）。開卡就吃素材的話，逾期失敗等於
   白虧兩個特質，玩家會學會不開卡。
2. **期限怎麼計**：以賽季（年）為單位，`deadlineYear = 開卡年 + deadline − 1`
   （deadline=2 → 開卡年＋下一年共兩季，第三年開季失敗）。月為單位會讓期限受 S14
   的月推進節奏影響，難校準。`null` = 生涯結束前（永不逾期，退役收束才算）。
3. **失敗怎麼降階**：legend／route 失敗一律掉成生涯標籤，**不讓 legend 掉成史詩**
   ——那會讓史詩持有率被任務卡灌水，破壞 §14.2 驗收線。標籤無數值效果、不進合成樹
   （`kernel/modifiers.js` 讀不到它，已確認）。

### v4.2 三條規則落點

- 素材失效即失敗：步驟 3 檢核每張卡素材需求（正向 `has`／`hasCount`），素材不在身上
  就失敗——被其他任務卡吃掉與被合成消耗走同一條，差異只在通知指名誰吃的。
- 失敗通知不得靜默：`failed[].reason` 指名 eater（同結算點的消耗清單）；
  `state.quests.log` 記 `{year,month,questId,tier,key,by}`，S17a 查詢層與 §15.5 傳記
  答得出「哪張卡吃掉哪個素材、什麼時候」。
- 同結算點按開卡時間排序，先開先吃；順序寫死才有可預測性。

### 有意義的坑（寫給下一站）

- ⚠ `questBeats` 內層變數不可叫 `card`——shared.js 的 `card()` 是卡片產生器，
  遮蔽後 `yield card(...)` 直接炸 `card is not a function`。
- ⚠ 條件式求值器是純函式：不得改 state；`collectMaterials` 只收**正向** `has`／
  `hasCount`（`not has` 不算素材）。
- ⚠ 觸發與達成在同一結算點都成立 → 開卡當下瞬間達成（引擎允許）。卡表設計責任：
  達成目標必須比觸發門檻高（假卡已遵守）。
- ⚠ `fresh()` 測試 helper 的 `deadline ?? 2` 會吃掉 `deadline: null`，要用
  `=== undefined` 判斷。
- 強制退役收束是「目標已滿足照發」——達成迴圈**不**因 `forced` 跳過（先做錯過，
  退役時所有進行中卡全判失敗，目標達成的卡也白死；已在 `tests/kernel/quests.mjs`
  鎖住）。
