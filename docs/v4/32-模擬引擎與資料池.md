狀態：未開始

推理難度：中
建議模型：Sonnet 5（`claude-sonnet-5`）
理由：公式與 schema 由 S31 定案，本站照做。判斷點在種子化與批次結算的效能

## 為什麼做這件事

賽區內 NPC 隊伍間的對戰目前不存在——引擎只有玩家隊的團隊強度與聚合對手
（§11.1），其他隊伍的勝負從沒被模擬過（§21.3 的戰績排名 UI 備忘因此掛到現在）。
本站把 §24.2 的宏觀層落地：NPC 隊伍基礎狀態匯入＋純數學批量模擬引擎，產出
整月賽程的勝負與局數，並把積分榜接上 §22.1 的「戰績排名（資料待接）」格。

## 範圍

### 要做

**1. NPC 隊伍狀態匯入**

- 依 S31 定案：從 `npc_roster.json`（庚組 S27 產物）匯入主場賽區各年代的
  隊伍與選手狀態，照 S29 逐選手模型的構成規則組隊。
- 隊伍與 `data/regions/home.js` 的 `timeline.teams` 對齊（史實隊名），
  縮寫顯示沿用庚組 S28 的鏈。

**2. 宏觀批量模擬引擎**

- 照 S31 定案的公式：純數學批次結算整個月賽程——每場勝負與局數（Bo3）。
- 種子化：NPC 對戰用同一 rng 來源，測試可重現（§20.3 精神）。
- 效能驗收：整月賽程瞬間結算（無感知延遲），寫進交接筆記實測值。

**3. 聯賽積分榜與資料池**

- 依 S31 定案的 schema 建資料池：寫入每場宏觀結果。
- 積分榜計算（勝場／局數／排名），產出給 §22.1 主畫面狀態帶。
- §21.3 的「隊伍交戰戰績排名（UI 備忘）」條目標記關閉；§22.1 的「資料待接」
  改為實際資料源。

### 不要做

- 不做微觀數據（KDA／DPM）——S33 的事
- 不碰玩家數據接入與相對評價（S34）與國際賽（S35）
- 不推翻 S31 的公式與 schema

## 要動的檔案

| 檔案 | 動作 |
| --- | --- |
| `src/engine/`（模擬引擎落點依 S31 定案） | 批量模擬引擎 |

| `src/phases/`（賽程結算消費端） | 月結算接模擬 |
| `tests/` | 種子可重現、積分榜正確性測試 |

---

## 規則與不變式

- 背景結算零 LLM（§24.1）——模擬引擎內不得有任何網路或模型呼叫
- `npm test` 全綠；`history/` 分區（賽制史實）不動
- 同種子同賽程必同結果（決定性重算成立）

- 160 段 smoke 不受影響（模擬引擎不進玩家隊強度計算，除非 S31 定案說要進——
