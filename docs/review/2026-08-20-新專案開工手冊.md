# 新專案開工手冊（依 esportlife 68 站檢討重寫）

> 2026-08-20。配套讀物：`2026-08-20-token消耗事後檢討.md`（本檔的所有數字都出自那份實測）。
> 適用對象：由 AI agent 逐站施作、預計 20 站以上、單一 session 吃不下的長期專案。
> 20 站以下請直接跳到第八章「什麼時候不要用這套」。

---

## 〇、三條總則

整份手冊都是這三條的展開。記不住其餘的，記住這三條。

### 總則一：每條知識都要選一個付費模式

同一件事寫在不同地方，成本差兩個數量級：

- 寫進**規則檔**（每 session 注入）：成本 ＝ token × 每站 × 站數。
- 寫進**測試**：成本 ＝ 0，直到它壞掉。
- 寫進**腳本**：成本 ＝ 0，永遠。
- 寫進**按需拉取的文件**：成本 ＝ token × 真的需要的那幾站。

esportlife 的雙註冊表規則選錯了付費模式：測試（`tests/kernel/conditions.mjs`）已經在守，
規則檔卻還付 979 token／站，68 站約 66,600 token，買的是 `npm test` 0.8 秒就抓得到的事。

**每寫一條規則，先問它該用哪種模式付費。「寫進規則檔」是最後手段，不是預設。**

### 總則二：有唯一正確答案的，交給腳本

判準一：這件事有沒有唯一正確答案。有，就是腳本的工作。
判準二：這個提示如果被忽略，誰會發現。沒人發現，它就不是保護，只是安慰。

腳本不只省 token，是省錯誤——腳本不會忘、不會漂移、失敗會叫。

### 總則三：每件事實只有一個家

esportlife 每站把同一件事寫進四個地方（交接筆記／狀態表／工作日誌／變更記錄），
結果 126 條長句重複出現 299 次，文件體積長到程式碼的兩倍（1,986,537 bytes 對 33,279 行），
刪除率只有 1.1%。

**一個家，其餘由腳本生成。**

## 一、開工前（Day 0）

Day 0 的每個決定會被乘以站數。esportlife 貴的部分全部是第一週決定的，然後付了 68 次。
以下八步照順序做完再寫第一行程式，成本約一站工作量。

### 步驟 1：先定「站」的切法，並且是機器可讀的

站 ＝ 一個 session 吃得下的工作單位。第一天就要決定站的資料長什麼樣，而且**它是資料檔，
不是散文**。

建 `project/stations.json`：

```json
{
  "stations": [
    { "id": "S01", "name": "資料層地基", "doc": "docs/stations/01-資料層地基.md",
      "status": "not-started", "prereqs": [], "difficulty": "中", "model": "sonnet",
      "spec": ["§2", "§3.1"], "files": ["src/data/**"], "estimate": 250 }
  ]
}
```

⚠ **不要把狀態表寫成 markdown 表格再叫腳本去解析它。** esportlife 就是這樣，於是表格旁邊
長出一段隨站數滾動增長的「現況」散文（4,690 bytes，從不裁切），而狀態表本身已經有那些資訊。
資料是資料，`README.md` 是**生成的視圖**。散文沒有地方可以附著，就不會附著。

`estimate` 欄位是規模上限的守門員（步驟 7）。`spec` 與 `files` 是簡報腳本的切片依據（步驟 4）。

### 步驟 2：先寫預算腳本，再寫任何文件

**這一步最反直覺，也最有效。**

esportlife 的前置長到 31,532 token 沒有任何人發現，因為沒有東西在量。有了量測，
每次加文件都會看到價格。

`tools/budget.mjs`，約 40 行：估算「開一站要載入多少 token」，超過門檻就非零退出，
進 `npm test`。門檻建議 8,000。

估法夠用就好（CJK 每字約 0.95 token、ASCII 每 4 字約 1 token），重點是**趨勢可見**，
不是絕對精準。

### 步驟 3：定四個檔案的職責，並寫下各自的壽命與讀者

開工前把這張表釘死，之後每份文件出生時都要能歸到其中一類：

- **規則檔**（`AGENTS.md`）：每 session 注入。讀者是每一站。壽命永久。**硬上限 1,000 token。**
- **規格**（`docs/spec/`）：按 § 切片拉取。讀者是需要那一節的站。壽命永久。
- **決策紀錄**（`docs/spec/decisions.md`）：**預設永不載入**。讀者只有「要改這個數字的那一站」。
  壽命永久，成本趨近零。
- **交接筆記**（站說明書尾）：讀者只有下一站。**壽命到下一站完工為止**，然後壓成兩節。
- **工作日誌**（`WORKLOG.md`）：讀者是人。每條上限 15 行，只寫意圖，滿 30 條封存。

esportlife 缺的就是「壽命」這一欄：交接筆記寫完就永久留著，長到 `docs/v4` 的 43%。

### 步驟 4：寫工作流腳本骨架（一支 CLI，不要六支散腳本）

`tools/station.mjs`，五個子命令。第一天先寫 `next` 與 `budget`，其餘隨第一站補完：

- `station next`：從 `stations.json` 解出下一個可做的站（前置全完成、狀態未開始），
  含前置完整性檢查。解析失敗當場修，不准人肉看檔開工。
- `station brief <id>`：**開工簡報組裝器，整套的核心。** 輸出一份，取代所有全檔讀：
  - 該站的 `stations.json` 條目；
  - 各前置站交接筆記的「給下一站」小節（只有這一節）；
  - 依 `spec` 欄位從 `docs/spec/` 切出指名章節；
  - 依 `files` 欄位從審查規則檔帶出對應的 path-scoped 規則；
  - 基準快照的數字段（不含敘述）。
- `station done <id>`：機械更新狀態、跑封存檢查。收尾不該為了改一個字重讀整份文件。
- `station budget [id]`：步驟 2 的預算量測。
- `station reap`：掃出過壽命的文件（交接筆記、超量工作日誌）並報告。

⚠ **腳本寫了就要把全讀撤掉。** esportlife 的 `next-station.mjs` 早就在解析狀態表，
但動工 skill 仍要求讀 `README.md` 全檔 12,882 token——兩份成本都在付。

### 步驟 5：先立不變式骨架，再寫內容

測試框架與「不變式」這個概念要在第一站之前就位，因為**不變式是規則檔的替代品**，
沒有它，規則就只能寫進提示。

第一天先建三類守門測試的空殼：

- **註冊表同步**：任何「加一個東西要同時改兩處」的地方，寫雙向差集測試。
  esportlife 的 `QUERIES`／`PREDICATES`、`COND_KINDS`／`COND_NODES` 就是這類，
  而且它們證明了這類測試有效。
- **單一來源**：跨檔字串比對必須**過寫入端的實際運算式**，不得手抄預期字串（手抄只是把
  bug 抄第二遍）。
- **硬約束**：像「教練戰力點平均必須是 2.0」這種動一個就要補回來的全域約束。

規則：**新測試要先紅過才算守得住。**

### 步驟 6：決定「數字的家」，並且只有一個

- 常數住在程式碼（`src/data/*.js`），**理由寫在該檔檔頭註解**——住在唯一會改它的人一定會
  打開的檔案裡，只有那個人付 token。
- 規格書裡的表格是**生成的視圖**（`<!-- gen:XXX -->` 區塊），由 `tools/spec.mjs gen` 從資料
  模組重寫，加測試比對生成結果與檔案內容。

esportlife 的 `src/data/coaches.js` 檔頭是這件事的正確示範：講清楚為什麼這樣設計、
警告硬約束、指名守門測試、解釋特殊寫法。可以直接當範本。

### 步驟 7：定規模上限與拆站規則

額度中途耗盡是隱性成本最高的失敗模式——續接的 session 要**重付一次完整前置**。

- 站說明書寫完先估：超過 400 行 diff 或跨 3 個以上模組，先拆站再開工。
- 一個 session 只做一站。
- 做不完不要硬撐：把做到哪裡寫進交接筆記、狀態改「進行中」、commit 現況，然後停。
- 校準／收斂型的站獨立成站，不要混進功能站（esportlife 的 S30／S36／S50 證明有效）。

### 步驟 8：寫規則檔與動工 skill（範本見第四章）

最後才寫提示，而且**寫的時候預算腳本已經在跑了**，超線立刻看得到。

## 二、開工中（每站的固定循環）

### 開工（三步，不要更多）

1. `node tools/station.mjs next` 抓下一站。腳本解析失敗當場修，不准跳過腳本人肉開工。
2. 使用者確認要做哪一站（附難度與建議模型；並行可做的站一併列出）。
3. `node tools/station.mjs brief <id>`，**只讀它的輸出**。不再開 `README.md`、不再開規格書全檔、
   不再開共通規則全檔。

前置預算 8,000 token 以下。超線是腳本的 bug 或站切太大，不是「這次特別複雜」。

### 施作

照說明書的「要做／不要做」。不碰其他站的檔案。

有疑問時的取用順序（由便宜到貴）：先看守門測試（它就是規格的可執行版）、再切規格的指名章節、
再拉決策紀錄條目、最後才問使用者。

### 收尾（順序固定，不要跳）

1. 跑測試。
2. 回填交接筆記（範本見第四章，只有三節）。
3. `node tools/station.mjs done <id>`——機械更新狀態，順帶跑封存檢查。
4. 工作日誌加一筆，上限 15 行，只寫意圖與脈絡。
5. 審查閘門（下一節）。
6. commit、push。

### 審查閘門（委託模式）

esportlife 的 `scripts/station-review.mjs` 是全專案最佳實踐，**直接照抄**：

- **確定性工程給腳本**：測試閘門、待審檔篩選（自動排除 `*.md`）、path-scoped 規則解析、
  diff 組裝。全程不呼叫 LLM、不需 API key，本身幾乎不花錢。
- **語意判斷給 agent**：逐檔審查意見，寫成結構化 JSON 再進閘門。
- critical／high 擋 commit，逐條修到過；medium／low 修掉或記進交接筆記，不得無聲忽略。

⚠ 審查包對未追蹤檔附全文那條要加上限（超過 200 行只附前 100 行加結構摘要），
否則新增大檔時整檔進上下文。

### 每站結束的兩個檢查（各一分鐘）

- `station budget` 有沒有往上漂？漂了就是有人偷加文件進前置。
- 這一站寫的規則，有沒有哪一條其實可以是測試？可以就改成測試。

## 三、需要的工具

全部零相依、原生執行即可。Node 沒有內建 YAML 解析器，要機器可讀格式就用 JSON。

1. **`tools/station.mjs`**（約 250 行）：`next`／`brief`／`done`／`budget`／`reap` 五個子命令。
   整套的核心，其中 `brief` 值最多。
2. **`tools/spec.mjs`**（約 120 行）：`slice §5.3 §7`（按 § 切規格）、`gen`（從資料模組生成
   規格表格區塊）、`check`（比對生成結果，進測試）。
3. **`tools/review.mjs`**（約 200 行）：委託模式審查包，照 esportlife 的 `station-review.mjs`。
4. **測試檔 `tests/rules.mjs`**（隨專案長）：註冊表雙向差集、單一來源比對、硬約束、
   文件壽命與預算上限。**規則檔瘦不下來的部分，全部在這裡。**
5. **CLI 輸出過濾器**（rtk 或等價工具）：管的是指令輸出，與文件載入不重疊，兩邊都要。

⚠ 六支散腳本不如一支帶子命令的 CLI：少一份記憶負擔，也少一次「這個功能在哪支腳本裡」的搜尋。

## 四、該寫什麼提示（可直接套用的範本）

### 規則檔 `AGENTS.md`（硬上限 1,000 token，由測試守）

只放**不隨檔案變動、每一站都真的需要**的內容：

```markdown
# 專案規則

## 動工
說「動工」即跑 `node tools/station.mjs next`，選定後跑 `brief <id>`，只讀它的輸出。
不要重跑搜尋理解進度，不要開全檔。

## 收尾（順序固定）
測試 → 回填交接筆記 → `station done <id>` → 工作日誌一筆（≤15 行）→ 審查閘門 → commit → push。
一個 session 只做一站。做不完就寫進交接筆記、狀態改「進行中」、commit 現況，然後停。

## commit 格式
站工作 `feat: <站號> <主題>——<一句話>`；審查修正 `fix: <站號> review 修正——<改了什麼>`；
只記不改 `docs: <站號> review 補記——<N 條記入交接筆記>`。

## 規則要寫在哪
任何約束先問能不能用測試守。能，就寫測試，本檔只留一行指路。
本檔的成本是「每 session × 每站」，測試的成本是「壞掉時才付」。
path-scoped 的工程規則寫進審查規則檔，由 `brief` 按本站要動的檔案注入。

## 已經有測試在守的（本檔不重複，壞了會紅）
- 註冊表雙向同步：`tests/rules.mjs`
- 單一來源字串比對：`tests/rules.mjs`
- 硬約束：`tests/rules.mjs`

## 回覆風格
技術精確前提下最小化 token。去冗言、短詞、無表格、無表情符號。
否定詞與數字單位絕不可省。工具呼叫前不輸出前言與計畫。
例外（恢復完整句）：安全警告、不可逆操作確認、多步驟順序易誤解、壓縮造成技術歧義。
```

⚠ **不要寫進規則檔的東西**：任何 path-scoped 的工程規則（進審查規則檔）、任何測試守得住的
不變式（寫測試）、任何工具的完整指令表（那是查得到的文件）、任何專案現況敘述（那是狀態表）。

### 站說明書範本

```markdown
# <站號> · <站名>

必讀規格：§X.Y、§Z    要動的檔案：src/...    預估規模：<行數>    難度：<高/中/低>

## 為什麼做這件事
問題是什麼，這一站的解法是什麼。讓不知道前因的人讀得懂。三到五句。

## 入口狀態
現在這塊長什麼樣、哪些前置已經到位。

## 範圍
### 要做
### 不要做
（明列不准碰的檔案與不准順手做的事）

## 規則與不變式
只列本站相關的。指得出守門測試的寫成一行加檔名，指不出的就是這一站要補的測試。

## 完成定義
可驗證的條件，不是形容詞。

## 交接筆記
（收尾時回填，見下）
```

### 交接筆記範本（只有三節，這是壽命規則的載體）

```markdown
### 給下一站
下一站真正需要的輸入：留下的介面、量到的數字、埋的 TODO。

### 刻意沒做
以及為什麼。程式碼裡對應的 TODO 在哪。

### 偏離說明書之處
每一條註明是否經使用者拍板。
```

⚠ **後續站完工後，把這份壓回這三節，其餘刪除。** 施作過程的敘述在 git 裡，不必留在
會被載入的檔案裡。這條沒有腳本守就一定會爛掉——所以 `station reap` 要報告它。

### 動工 skill

```markdown
使用者說「動工」時，依序執行，不要跳步。

1. `node tools/station.mjs next`。解析失敗先修腳本，不准人肉看檔開工。
2. 把下一站與可並行的站列成選項問使用者（label 附難度與建議模型，下一站標「推薦」）。
   選定後先提醒切換到建議模型。
3. `node tools/station.mjs brief <id>`，只讀它的輸出。不要另外開全檔。
4. 照說明書的「要做／不要做」施作。
5. 收尾照規則檔的固定順序。
```

### 審查規則檔（path-scoped，JSON）

```json
{ "rules": [
  { "path": "src/data/**",
    "rule": "單一來源：名次表、階名、旗標名只准一份手抄本；存機器可讀的鍵，顯示字串由鍵導出。發現跨檔重複定義或解析顯示字串，標為缺陷。" },
  { "path": "**/*.{js,mjs}",
    "rule": "零建置、零相依、原生 ESM、Node 原生測試。不要建議引入建置工具、打包器或新套件。" }
] }
```

這份檔案同時是 `brief` 的注入來源與審查閘門的規則來源——**一份規則，兩處消費，零手抄**。

## 五、防再膨脹的機制

沒有強制機制，上面每一條都會在三十站內爛回原狀。四道棘輪，全部進 `npm test`：

1. **前置預算**：`station budget` 超過 8,000 就紅。文件加不進去，只能想辦法讓它值得。
2. **規則檔行數上限**：`AGENTS.md` 超過 1,000 token 就紅。逼人回答「這條為什麼不能是測試」。
3. **文件壽命**：`station reap` 掃出過壽命的交接筆記與超量工作日誌，收尾時報告。
4. **生成檔一致性**：規格書的生成區塊與資料模組不一致就紅。手抄第二份會被當場抓到。

⚠ 這四道不是可選的。esportlife 每一條規則都寫得很清楚，但沒有一條被強制，
所以文件刪除率是 1.1%——寫進去的東西實際上永遠不會被拿掉。

## 六、esportlife 的六個教訓對照

每一條都是實測，不是推測。細節見檢討報告。

1. **前置沒人量就會漲到 31,532 token**，其中 26,036 與站無關、68 站各重付一次，
   約 177 萬 token。對策：步驟 2 的預算腳本，第一天就寫。
2. **腳本寫了但全讀沒撤**：`next-station.mjs` 已解析狀態表，動工流程仍讀 `README.md`
   全檔 12,882 token（載入率 2%）。對策：步驟 4 的「撤掉全讀」是腳本的完成定義之一。
3. **測試守得住的事還在付提示費**：979 token／站買 `npm test` 0.8 秒抓得到的事。
   對策：總則一，每條規則出生時就選付費模式。
4. **同一事實抄四份**：126 條長句重複 299 次。對策：總則三，一個家，其餘生成。
5. **文件沒有壽命**：交接筆記長到 `docs/v4` 的 43%，刪除率 1.1%。
   對策：步驟 3 的壽命欄位 ＋ 第五章的 `reap` 棘輪。
6. **警告不是保護**：全規格書 40 行 ⚠，只有 13 行指得出守它的測試。
   四分之三的警告沒有任何東西在守。對策：步驟 5，不變式先於內容。

## 七、刻意不腳本化的

這些需要理解意圖，腳本化只會產出格式正確的廢話：

- 工作日誌的「方向」段（這條為什麼存在）。
- 校準判讀（數字漂了，是機制變差還是樣本重排）。
- 站的拆法與範圍決定。
- 版本級別（大／中／小改版）的判斷。
- 審查意見本身。

⚠ 反過來也要守住：**別把上面五項以外的東西留給模型判斷。**

## 八、什麼時候不要用這套

這套的建置成本約一到一點五站工作量，回收點在第八到第十站左右。

- **預估 10 站以下**：只做步驟 2（預算腳本）與步驟 5（不變式）。其餘全是負擔。
- **單人短期原型**：全部不要。文件的價值來自「下一個 session 讀得懂」，
  原型沒有下一個 session。
- **每站範圍差異極大、無法用同一份說明書格式**：先想清楚站的切法，切法沒定之前
  建工具是在自動化一個還沒成形的流程。

⚠ 唯一在任何規模都值得的是**預算量測**。它便宜（約 40 行），而且沒有它，
其餘所有問題都是隱形的。

## 九、第一週時程建議

- **Day 0 上午**：步驟 1（站切法與 `stations.json`）、步驟 3（四個檔案的職責與壽命）。
- **Day 0 下午**：步驟 2（預算腳本）、步驟 5（不變式骨架與測試 runner）。
- **Day 1**：步驟 4（`station.mjs` 的 `next` 與 `budget`）、步驟 6（數字的家）、
  步驟 7（規模上限）、步驟 8（規則檔與動工 skill）。
- **Day 2 起**：第一站。做完第一站再補 `brief`／`done`／`reap`——
  **等有一站的真實資料再寫簡報組裝器，比憑空設計準得多。**
- **第三站結束**：回頭跑一次 `station budget`，看前置有沒有開始漂。這是第一個檢查點。
