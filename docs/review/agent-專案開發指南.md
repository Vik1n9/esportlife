# AI Agent 專案開發指南

> 通用流程指南，與語言、框架、工作單位切法無關。
> 證據來源：`2026-08-20-token消耗事後檢討.md`（一個 68 個工作單位、2MB 文件的真實專案實測）。
> 文中引用的數字都出自那份實測，但流程本身不依賴那個專案的任何設計。

## 這份指南要解決的問題

由 AI agent 長期施作的專案，成本不是花在「做事」，是花在**每個 session 重新理解專案**。
這筆錢的特性是：

- 它是**乘法**——每 session 的前置 × session 數。
- 它**不可見**——沒有工具會告訴你前置漲了。
- 它**只增不減**——文件是追加式的，沒有機制就不會有人刪。

來源案例的實測：前置 31,532 token，其中 26,036 與當次任務無關，68 次各重付一次，
約 177 萬 token；文件體積長到程式碼的兩倍，刪除率 1.1%。

**核心心法**：每一條知識都要選一個付費模式。

- 寫進**規則檔**（每 session 注入）：成本 ＝ token × 每 session × session 數。
- 寫進**測試／檢查**：成本 ＝ 0，直到它壞掉。
- 寫進**腳本**：成本 ＝ 0，永遠。
- 寫進**按需拉取的文件**：成本 ＝ 只有真的需要的那幾次付。

「寫進規則檔」是最後手段，不是預設。整份指南都是這句話的展開。

## 步驟 0：開工前的工具配置

目標：讓 agent 有**一個指令可以確認自己沒把東西弄壞**，而且那個指令又快又安靜。

以下按重要性排序。前四項是任何規模都要有的，後四項看專案大小。

### 0.1 一個統一的驗證入口（最重要的單一項目）

不管專案用什麼技術，都要有**一個指令**，它的退出碼就代表「可不可以提交」：

```
make check     |     npm test     |     just check     |     ./check.sh
```

它內部串起 lint、型別檢查、單元測試，任何一項失敗就非零退出。

為什麼是第一名：agent 判斷「我做完了嗎」只有兩種方式——問人，或跑這個指令。
沒有它，agent 只能靠讀程式碼推測，那既慢又不可靠。

⚠ **不要讓 agent 需要記住三個指令。** 記住的成本是每 session 付，統一入口的成本付一次。

### 0.2 快到願意跑

驗證超過 60 秒，agent 就會開始「這次應該沒問題吧」。分層：

- **秒級**：格式化、lint、型別檢查。每次改完都跑。
- **分鐘級**：單元測試。提交前跑。
- **慢的**：端對端、整合、大量模擬。預設不跑，明確要求才跑。

在統一入口裡預設只跑前兩層，慢的掛在 `make check-all` 或 CI。

### 0.3 輸出過濾

測試框架與建置工具預設對人類友善——進度條、色碼、逐項通過訊息。這些對 agent 是純浪費。

- 測試用 dot／quiet reporter，**只輸出失敗**。
- 建置工具關掉進度動畫（多數有 `--no-progress`、`--reporter=` 之類的旗標）。
- 沒有旗標可用時，包一層過濾（通用工具如 rtk，或自己寫十行的 grep 包裝）。

一次 verbose 的測試輸出動輒數千 token，而其中有用的資訊是零（全綠）或幾行（失敗）。

### 0.4 格式化自動修，不要讓 agent 手動處理

格式化與可自動修的 lint 全部設成自動執行（pre-commit hook 或 `--fix`）。
agent 花在對齊縮排上的每一個 token 都是浪費，而且改錯的機率不低。

### 0.5 權限允許清單

把只讀指令加進 agent 的允許清單（Claude Code 是 `.claude/settings.json`），
避免每次跑 `git status`、`ls`、測試都要人按同意。中斷本身也是成本。

⚠ 只放**只讀**與**可逆**的。刪除、推送、部署留在需要確認的那一側。

### 0.6 環境可重現

新 session 拿到乾淨環境要能直接跑驗證。一支 `setup.sh` 或啟動 hook，
把相依安裝、環境變數、資料庫初始化包好。

否則每個 session 的前十分鐘都在重新發現「喔要先裝這個」。

### 0.7 只裝真的會用到的 agent 工具

每一個掛上去的 MCP server、每一個工具定義，**它的 schema 在每一次請求都會被送出**。
裝了不用的工具是持續付費的裝飾品。

原則：這個工具這個月用過嗎？沒有就拆掉，需要時再裝。

### 0.8 預算量測（最反直覺，但值得）

寫一支四十行的腳本，估算「開始一個任務要載入多少 token」，超過門檻就非零退出，
掛進統一驗證入口。

估法夠用就好（中日韓文每字約 0.95 token、ASCII 每 4 字約 1 token），
重點是**趨勢可見**。來源案例的前置漲到 31,532 token 沒有任何人發現，就是因為沒有東西在量。

有了它，之後每次想加文件都會看到價格。

## 步驟 1：規則檔（AGENTS.md／CLAUDE.md）怎麼寫

規則檔是**每個 session 都會被注入**的東西，所以它是全專案最貴的每字成本。
寫規則檔的技巧，九成是**決定什麼不寫進去**。

### 1.1 先定預算，再寫內容

**硬上限：1,000 token，約 40 行。** 這個數字不是精算來的，它的作用是**強迫取捨**——
沒有上限，規則檔一定會長成來源案例的 10.5KB。

上限要由檢查腳本強制（步驟 2），不能只是口頭約定。

### 1.2 只有五類東西該進去

1. **專案不變的事實**：技術棧一句話、跑什麼指令驗證、目錄分層與依賴方向。
2. **流程順序**：收尾的固定步驟，以及「做不完的時候怎麼停」。
3. **輸出格式**：commit 訊息格式、回覆風格、PR 慣例。
4. **指路**：詳細規則在哪個檔、守門測試在哪、專屬腳本怎麼用。
5. **無法用測試表達的禁令**：例如「不要引入新相依」在某些專案可以用測試守，
   在某些專案只能靠規則檔。

判準：**這條規則，是不是每一個 session 都真的需要，而且沒有更便宜的表達方式？**

### 1.3 六類東西絕對不要進去

1. **測試守得住的不變式。** 來源案例把「加謂詞要同時改兩張註冊表」寫進規則檔
   花 979 token／session，而測試檔早就在做雙向差集比對了——買的是驗證指令 0.8 秒
   就會抓到的事，68 次共約 66,600 token。
2. **只有動到特定檔案才需要的規則。** 這些屬於 path-scoped 規則檔（步驟 3.4），
   由腳本按「這次要動哪些檔案」注入。
3. **工具的完整指令表。** 那是查得到的文件。留三條核心用法就好。
4. **專案現況敘述。** 「目前已完成 A、B、C，正在做 D」屬於狀態資料，不屬於規則。
   寫進規則檔它就會隨專案進度無限增長。
5. **通用工程教學。** 「函式要短」「命名要清楚」——模型已經知道，寫了只是佔位置。
6. **架構文件全文。** 貼指路，不貼內容。

### 1.4 每一條規則都要標註「誰來執行」

這是讓規則檔不會再膨脹的關鍵習慣。每條規則後面標一個執行者：

```
- 依賴方向 ui → service → data，不得反向    [由 tests/arch 守]
- commit 格式 <type>: <scope>——<一句話>      [由 review 閘門守]
- 做不完就寫進交接筆記然後停，不要硬撐        [只能靠這裡]
```

標不出執行者的，先問「那它被違反時誰會發現」。答案是「沒人」的話，
這條規則不是保護，是安慰——刪掉，或補一個守門。

### 1.5 寫法

- **祈使句，可驗證。** 寫「新增相依前先問使用者」，不要寫「請謹慎管理相依」。
- **具體檔名與指令**，不要寫「相關設定檔」。
- **禁止「請記得」開頭的句子。** 記不住就該是測試。
- **否定詞與數字絕不省略。** 壓縮語句時最先掉的就是這兩樣，代價最高。
- **不要寫理由。** 理由屬於決策紀錄。規則檔只寫規則本身加一個指路。

### 1.6 分層：根目錄 vs 子目錄

多數 agent 工具支援子目錄的規則檔，只在動到該目錄時才載入。善用它：

- 根目錄規則檔：全專案共通，最短。
- 子目錄規則檔：那一塊特有的約定，只有動它時才付費。

這是免費的按需載入，不需要自己寫腳本。

### 1.7 範本

```markdown
# 專案規則

## 事實
<技術棧一句話>。驗證：`make check`（lint＋型別＋單元測試，約 20 秒）。
依賴方向 <A> → <B> → <C>，不得反向。

## 流程
開工：跑 `./tools/dev.sh brief <任務>`，只讀它的輸出，不要另外開全檔。
收尾：`make check` → 回填交接筆記 → `./tools/dev.sh done <任務>` → 審查閘門 → commit → push。
做不完：把進度寫進交接筆記、狀態改「進行中」、commit 現況，然後停。不要硬撐。

## 格式
commit：`<type>: <範圍>——<一句話總結>`。
回覆：技術精確前提下最小化 token；無表格、無裝飾；否定詞與數字不可省。

## 規則寫在哪
任何約束先問能不能用測試守。能，就寫測試，本檔只留一行指路。
本檔成本是「每 session × 每次」，測試成本是「壞掉時才付」。
本檔上限 1,000 token，由 `make check` 強制。
path-scoped 的工程規則寫在 `.review/rules.json`，由 brief 按本次要動的檔案注入。

## 已經有守門的（本檔不重複）
- 架構依賴方向、註冊表同步、單一來源比對：`tests/rules.*`
- 格式與 lint：pre-commit 自動修
```

## 步驟 2：把規則變成守門（規則檔瘦身的前提）

這一步夾在「寫規則」與「寫腳本」之間，因為**規則檔瘦不下來的部分，全部要有地方去**。
沒有這一步，步驟 1 的上限就只是把規則刪掉而已。

### 2.1 三類幾乎每個專案都需要的守門

1. **註冊表同步**：任何「加一個東西要同時改兩處」的地方，寫**雙向差集**測試。
   這類 bug 靜悄悄（打錯鍵不會報錯，只是沒有效果），最值得自動化。
2. **單一來源**：跨檔比對必須**過寫入端的實際運算式**，不得手抄預期值——
   手抄只是把 bug 抄第二遍。
3. **架構約束**：依賴方向、禁止的 import、禁止的相依。多數語言都有現成工具，
   沒有就寫十幾行掃 import。

### 2.2 錯誤訊息要能自我修復

**這是最容易被忽略、投資報酬最高的一件事。**

守門失敗時的訊息，是 agent 唯一會讀到的東西。寫成這樣沒有用：

```
FAIL: registry mismatch
```

寫成這樣，agent 不必讀任何文件就能修好：

```
FAIL 註冊表不同步：`percentile` 在 engine/queries 有、在 tools/schema 沒有。
兩處都要加。加謂詞的完整步驟見 tests/rules.js 檔頭。
```

**把規則寫進錯誤訊息裡**，比寫進規則檔便宜——只有在真的違反時才付這些 token。

### 2.3 新守門要先紅過

寫完守門，先故意破壞一次確認它會紅，再修回來。沒紅過的守門有相當高的比例
根本沒在檢查（斷言寫反、比對到空集合、測試沒被 runner 掃到）。

### 2.4 守門也要管文件

除了程式碼，這幾項值得寫成檢查：

- 規則檔字數上限。
- 前置載入預算上限。
- 生成檔與來源不一致（若有從資料生成的文件）。
- 過壽命的文件（見步驟 3.5）。

## 步驟 3：建立專案專屬腳本

### 3.1 怎麼決定要寫什麼腳本

不要憑空設計。**做完三到五個真實任務，再回頭看自己重複做了什麼。**

三個判準，全中就該寫成腳本：

1. 這件事有**唯一正確答案**（不需要權衡）。
2. 它**每次任務都要做**。
3. 它的輸出**可以被裁剪**（現在是整檔讀，其實只要幾行）。

⚠ 反過來，需要理解意圖的不要腳本化——腳本化只會產出格式正確的廢話。

### 3.2 四支幾乎每個專案都需要的

**一、狀態查詢（`next` / `status`）**

回答「現在在哪、下一步是什麼」。關鍵是它**讀資料檔，不是解析散文**。

把任務清單存成 JSON（或任何結構化格式）：

```json
{ "tasks": [
  { "id": "T01", "name": "資料層地基", "doc": "docs/tasks/01.md",
    "status": "done", "deps": [], "size": "M",
    "spec": ["§2", "§3.1"], "files": ["src/data/**"] }
] }
```

⚠ **不要把狀態表寫成 markdown 表格再叫腳本去解析。** 表格旁邊會長出散文——
來源案例的狀態表旁邊長出一段隨進度滾動增長的「現況」段落，而狀態表本身已經有那些資訊。
資料是資料，人看的文件是**生成的視圖**。散文沒有附著點，就不會附著。

**二、上下文組裝（`brief`）——整套裡最值錢的一支**

把「開始一個任務要讀的 N 份文件」壓成一份切片簡報：

- 該任務的資料條目（從 `next` 的同一份 JSON）；
- 前一個任務留下的交接筆記，**只取「給下一步」那一節**；
- 依 `spec` 欄位從規格文件切出指名章節（多數 markdown 規格有天然的標題錨點，
  切片器約三十行）；
- 依 `files` 欄位從 path-scoped 規則檔帶出對應規則；
- 基準數字（如果專案有校準基線之類的東西），只要數字不要敘述。

來源案例的實測：這一支可以把前置從 31,532 壓到 8,000 以下。

**三、機械更新（`done`）**

收尾時把狀態改掉、跑壽命檢查。看起來很小，但沒有它，agent 為了改一個字
要把整份狀態文件讀進來——來源案例那份是 12,882 token。

**四、預算量測（`budget`）**

步驟 0.8 那支。跟其他三支放在一起。

### 3.3 腳本設計原則

- **一支 CLI 帶子命令，不要散腳本。** 六支散腳本要記六個路徑，還會出現
  「這個功能在哪一支裡」的搜尋成本。
- **輸出是給 agent 讀的**：無色碼、無進度條、無裝飾邊框；成功時安靜，失敗時具體。
- **解析失敗要當場非零退出**，不要 silently 降級成部分結果——半份簡報比沒有更危險。
- **腳本本身要有測試。** 它是所有任務的入口，壞掉的殺傷力比業務程式碼大。
- **零額外相依優先。** 用執行環境已經有的東西。腳本是基礎設施，不該有安裝步驟。

### 3.4 path-scoped 規則檔

把「只有動到某些檔案才需要」的工程規則抽成一份結構化檔案：

```json
{ "rules": [
  { "path": "src/data/**",
    "rule": "資料單一來源：同一份表只准一份手抄本；存機器可讀的鍵，顯示字串由鍵導出。" },
  { "path": "**/*.sql",
    "rule": "遷移一律可逆，每個 up 都要有對應的 down。" }
] }
```

**一份規則，兩處消費**：`brief` 按本次要動的檔案注入給 agent，審查閘門用同一份當審查基準。
零手抄。

### 3.5 文件壽命與回收

每份文件出生時就標壽命，`reap` 子命令定期掃：

- **永久**：規則檔、規格、決策紀錄。
- **到下一步為止**：交接筆記。下一個任務做完就壓成「給下一步」與「刻意沒做」兩節，其餘刪除。
- **滿 N 條封存**：工作日誌。主檔只留最近幾條，其餘切進封存檔。

來源案例沒有這一欄，結果交接筆記長到佔文件總量的 43%，而它們的讀者早就消失了。

### 3.6 寫了腳本，就要把舊流程撤掉

**這是最常見的失敗。** 來源案例的狀態查詢腳本早就寫好並在用，
但開工流程仍然要求讀狀態文件全檔——腳本與全讀兩份成本都在付。

腳本的**完成定義**要包含「舊的做法已經從規則檔與流程說明裡刪掉」。

### 3.7 審查閘門：確定性給腳本，語意給 agent

來源案例裡做得最好的一件事，值得直接照抄：

- **腳本做**：跑驗證閘門、篩出待審檔案、解析 path-scoped 規則、組裝 diff。
  全程不呼叫模型，本身幾乎不花錢。
- **agent 做**：實際審查，意見寫成結構化格式再進閘門。
- 嚴重問題擋提交，次要問題修掉或記進交接筆記，**不得無聲忽略**。

⚠ 審查包附未追蹤檔全文時要設上限（例如超過 200 行只附前 100 行加結構摘要），
否則新增大檔時整檔進上下文。

## 步驟 4：接手既有倉庫

既有倉庫的難處在於：文件已經長歪了，而且**你不知道哪些是真的**。
不要一上來就大改。四個階段，順序不能顛倒。

### 4.1 階段 A：測量，不改任何東西

第一個 session 只做測量。這些指令幾乎在任何倉庫都能跑：

```bash
# 文件與程式碼的比例（健康的專案文件遠少於程式碼）
find . -name '*.md' -not -path './.git/*' | xargs wc -c | tail -1
git ls-files | grep -E '\.(js|mjs|ts|tsx|py|go|rs|java|rb)

# 文件是不是純追加（刪除率低於 5% 就是從來不收斂）
git log --numstat --format='' -- '*.md' | awk '{a+=$1;d+=$2} END{print "+"a" -"d}'

# 每個 session 自動注入多少（規則檔）
wc -c AGENTS.md CLAUDE.md .cursorrules 2>/dev/null

# 最大的幾個文件（通常就是被整檔讀的那幾個）
find . -name '*.md' -not -path './.git/*' -exec ls -la {} \; | sort -k5 -rn | head

# 跨檔重複（同一句話出現在幾個檔案）
find . -name '*.md' -not -path './.git/*' -exec awk 'length($0)>40 {print $0}' {} \; \
  | sort | uniq -d | wc -l
```

還要回答四個問題：

1. **有沒有統一驗證入口？** 沒有的話，這是第一優先，比任何文件整理都重要。
2. **驗證要跑多久？** 超過兩分鐘，agent 實際上不會跑它。
3. **規則檔裡有多少條是測試守得住的？** 逐條標執行者（步驟 1.4），標不出來的先圈起來。
4. **開始一個典型任務要讀哪幾個檔？** 加總它們的大小，這就是你的前置成本。

### 4.2 階段 B：止血——只動載入路徑，不動內容

風險最低、見效最快，通常一到兩天：

1. **先加預算量測。** 在改任何東西之前建立基線，否則沒辦法證明改善。
2. **規則檔瘦身。** 照步驟 1.3 的六類逐條刪。已經有測試守的直接刪成一行指路。
   這一步通常能砍掉一半以上，而且**不會破壞任何東西**，因為刪掉的都是重複表達。
3. **撤掉已被腳本取代的全讀。** 檢查流程說明裡有沒有「讀整份 X」，
   而 X 的資訊其實某支腳本已經能給。
4. **補統一驗證入口**（如果階段 A 發現沒有）。

⚠ 這個階段**不要碰文件內容**。只改「什麼時候載入什麼」，不改「寫了什麼」。

### 4.3 階段 C：建立守門

把階段 A 圈起來的「標不出執行者」的規則逐條處理：

- 能寫成測試的，寫測試（先紅過），然後從規則檔刪掉。
- 只在特定檔案適用的，移進 path-scoped 規則檔。
- 兩者都不行的，才留在規則檔——而且要寫清楚為什麼留。

**優先處理「已經被違反過」的規則。** 翻 git 記錄找修 bug 的 commit，
那些就是最需要守門的地方，而且你有現成的重現案例可以拿來確認守門會紅。

### 4.4 階段 D：收斂內容（最後才做，風險最高）

到這裡前置成本已經降下來了，剩下的是文件本身的體積：

1. 定每件事實的**唯一的家**，其餘改成生成或刪除。
2. 給文件加**壽命**，寫回收腳本。
3. 把長文件按天然錨點**拆片**，讓切片器能取用。
4. 把「理由」類的內容抽成**預設不載入**的決策紀錄。

⚠ 這個階段會動到很多檔案，**一次做一類，每類一個 commit**。
文件大搬家搞砸的話很難看出哪裡壞了。

### 4.5 接手時的三條戒律

1. **不要相信既有文件說的。** 文件會漂移，程式碼不會。
   文件與程式碼衝突時，以程式碼為準，然後修文件。
2. **不要在還沒做過三個真實任務前重構流程。** 你不知道哪裡痛。
   先照現有流程做三次，記錄每次卡在哪、讀了什麼沒用的東西。
3. **不要把「整理文件」當成一個任務做完。** 它是每個任務的收尾動作。
   一次性大掃除三個月後就會長回來，除非棘輪（步驟 5）裝好了。

## 步驟 5：防再膨脹的棘輪

沒有強制機制，上面每一條都會在三個月內爛回原狀。
來源案例的每一條規則都寫得很清楚，但沒有一條被強制，所以文件刪除率是 1.1%。

四道棘輪，全部掛進統一驗證入口：

1. **前置預算超線就紅。** 文件加不進去，只能想辦法讓它值得。
2. **規則檔字數上限超線就紅。** 逼人回答「這條為什麼不能是測試」。
3. **過壽命文件掃描**，收尾時報告。
4. **生成檔與來源不一致就紅。** 手抄第二份會被當場抓到。

加一條寫進規則檔的元規則：

> 任何要寫進規則檔的約束，先問能不能用測試守。能，就寫測試，規則檔只留一行指路。

## 最小可行版本

- **短期原型、一次性腳本**：全部不要。文件的價值來自「下一個 session 讀得懂」，
