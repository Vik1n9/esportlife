## 二、結構上守住的東西

這些是 v4.5.3 的承重牆。改動如果會破壞其中任何一條，那不是「在穩定點上往前走」，
是要另外開一個穩定點。前六條承襲重建前（語義變了的會註明），後六條是重建立起來的新牆。

**① 依賴方向單向**：`data ← kernel ← phases ← engine ← ui`。
`engine/` 不 import `ui/`、不碰 `document`，所以整段生涯可以在 Node 裡跑完——
23447 項測試能存在，靠的就是這條。

**② 階段只匯出兩個東西**：`export const kind` 與 `export function* run(g, phase)`。
階段不 import `game.js`，沒有循環依賴。**新增一個賽事＝寫一個檔、註冊一行、年曆加一列。**
月回合的 `phases/month.js` 與五拍賽事序列 `phases/seriesEvent.js` 是同一個協定。

**③ 一年有哪些賽事是資料**：`data/formats/calendar.js` 一張表。月回合制後
`order = 月 × 10 + 檔位`；符號位置（`SPLIT_OPEN`／`MSI_SLOT`…）由
`engine/calendar.js` 依當年賽段數展開成實際月份——年份的形狀是算出來的，不是抄表。

**④ 賽區是實體**：一個賽區一個檔（`data/regions/*.js`），席位數、賽段數、外援名額、
隊名都住在同一個檔。賽段結構隨史實逐年演進（2015 春／夏 → 2025 三賽段）。

**⑤ 特質效果是資料**：`data/traits.js`／`epics.js` 自己宣告效果，消費端只問
`kernel/modifiers.js` 的 `bonus`／`factor`／`floorOf`／`capOf`／`flag`／
`lifecycleWindows`。四種運算刻意不合成單一 `apply()`。v4.3 起特質效果可自由掛載
在任一層（§14.4 掛載點全景表），效果鍵由編輯器（`tools/schema.js` 的 `EFFECT_KEYS`）
與引擎測試共同鎖定。

**⑥ 種子決定天賦，不決定人生**（語義變了）：出生流（玩家輸入的種子）決定起始屬性、
潛力天花板、天生特質（0／1／2 個）、心理底色、英雄池、業餘隊伍、生命週期參數；
人生流每局隨機抽。引擎本身仍是 `(出生種子, 人生種子, 選擇)` 的確定性函式——
測試靠它重現 160 段生涯。但**「同種子＝同一段人生」的保證已廢**（V4 §20.1 廢決定論），
`golden.json` 黃金種子快照隨之刪除——同種子可以反覆玩出不同的人生。

**⑦ 三層養成**（重建前是兩層）：玩家只經營六屬性（0–100）；十二技能是屬性加權
導出值，唯讀、不能直接加點；教練評價是評價層——薪資／試訓／續約／FA 全部讀它，
玩家看不見公式（`coachRating` 是內部值，UI 不得讀取）。位置身分靠技能權重保證，
不再靠屬性折疊。

**⑧ 條件語言唯一**：`engine/conditions.js` 的 `evalCond` s-expression——任務卡、
事件卡、特質授予、退役結局共用一套。⚠ 加謂詞要同時加進 `conditions.js` 的 `QUERIES`
與 `tools/schema.js` 的 `PREDICATES` 兩張註冊表，同一個 commit；脫節測試會直接抓。
`eventTrigger.js` 的 `whenHits` 已退役。

**⑨ 謂詞讀查詢層**：條件語言一律讀 `engine/ledger.js`（生涯軌跡帳本），不讀 raw
state 欄位。改一個欄位要改三個地方的坑，擋在查詢層。

**⑩ 一份資料一份來源**：名次序位 `data/formats/finishes.js`（三份手抄本已退役）、
版號 `src/version.js`、DEMO 期程 `engine/demo.js`（`DEMO_MONTHS`／`isDemo`…五個純函式）。
跨檔字串比對必須有測試，且測試要過寫入端的實際運算式。

**⑪ 內容由編輯器產**：事件卡／訓練卡／任務卡／特質／配方／天生特質一律用 `tools/`
表單編輯器產出（86 事件卡、60 訓練卡、25 任務卡、72 特質、18 配方全是它產的）。
欄位合法性的第一道閘在表單，第二道在測試。手寫資料檔可以，但要自備兩道閘的記憶。

**⑫ 傳說特質只由生涯任務卡發放**：不從配方合成、不從事件卡直接給。
20 張 `legend` 卡是傳說唯一發放口；5 張 `route` 卡給平庸局替代性生涯路線
（發史詩＋生涯標籤，不發傳說）。這是鐵則層級的決定——S07 的兩條傳奇不變式
全部經過這個發放口（S17b 生涯任務引擎）。

### 平衡不變式取代了黃金種子快照

`regression/invariants.mjs` 是 V4 的安全網核心：它不錄快照（決定論已廢，錄不了），
改守「這個遊戲之所以是這個遊戲」的性質——**巔峰上界、打法差距、頂端才兌現、傳奇
稀有度、位置身分、合成消耗、潛力衰減、心理是放大器、明星效應上界**。門檻一律寫成
**比例**（÷ 屬性上限／÷ 可成長空間），換刻度不必重刷基準。⚠ 它擋得住「性質變了」，
擋不住「平衡變得更差」——好壞仍要靠分布數字與人的判斷。

鐵則二仍在：位置身分不准被平均掉——任兩路權重 L1 距離 ≥ 0.10、每路前二重屬性
合計 ≥ 0.45、靈巧對輔助 ≤ 0.06。

## 七、怎麼算「還在這個基準上」

往前走的時候，用這四條自檢：

1. **`npm test` 全綠**，而且檢查數只增不減（基準 23447）——減少通常代表某條檢查
   被改成恆真或比對到 `undefined`。⚠ 例外：校准站動對手／對手強度後，生涯打進
   深輪的段數改變，**依樣本數迭代**的檢查（帳本逐里程碑、不變式逐事件）會跟著
   樣本縮——S30 校準 −228 項屬此類（逐條查過，非恆真化）；引用此基準的站要
   先分辨這一類，不是見減就報警。
2. **平衡不變式守得住**：門檻是比例制，紅了就是性質變了——要放寬門檻，先拿
   校準證據說話，不要改數字繞過。
3. **文件與程式碼對得上**：改了賽制或改了檔名，同一個 commit 要把 `ARCHITECTURE`
   的目錄樹、`ESPORT-DESIGN-V4` 的規則對應表、`WIKI` 的攻略一起帶到；版號動了
   `tests/kernel/version.mjs` 守的四份手抄本會逼你。
4. **辛組的額外約束**：§23.1 的四件定案（一次到位、去姓名、Liquipedia 主源、
   LLM 只做語意離線快取）與 §24.1 的三件定案（背景模擬零 LLM、兩套百分位母體並存、
   Bo5 高壓檢定過乘法鏈）動工前不可推翻——庚組（S23–S30）已收尾，細部規格由
   S31 站定案後回寫 §24。

承重牆（第二節）要動的話，先開下一份快照，不要就地改。
