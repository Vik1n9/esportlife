# S48 · 月度事件卡掛鉤訓練選項（§12.1 增訂）

狀態：✅ 完成（2026-08-19）
前置：S46
預估：1 session
推理難度：中
建議模型：Sonnet 5（`claude-sonnet-5`）
理由：一張傾向表 + 一個加權抽選 + 一個條件運算子，落點與界線本站已寫定。
難的部分（哪些卡不准被偏置）已經是規則不是判斷。唯一要小心的是**不要把加權
套到條件卡上**，說明書把它列為第一條紅線。

---

## 為什麼做這件事

月度事件卡目前與玩家當月做了什麼**完全無關**：`eventTrigger` 步驟 2／3 落到隨機池時
是 `rng.pick(availableEvents(...))`，均勻抽。於是打了一整個月 SOLO RANK 的人，
跟泡了一整個月健身房的人，看到的劇情機率一模一樣。

把當月的訓練選擇餵進抽選，兩件事同時發生：**沉浸感**（做什麼就容易碰到什麼），
以及**變相鼓勵玩家嘗試其他訓練**（不同選項通往不同的劇情面）。後者對 S46 之後的
六選一特別重要——六個選項在數值上是對稱的，劇情面是它們唯一的非對稱差異。

⚠ 動的是**月度事件卡的抽選機制**（`engine/eventTrigger.js` ＋ `data/events.js`），
不是訓練事件卡（那個 S16 起就已經分活動了）。

## 範圍

### 要做

**1. 傾向表（放 `src/engine/eventTrigger.js`，與四步演算法同檔）**

`events.js` 已有現成的分類軸 `sub`，**不必新增資料欄位**。90 張卡的分布：
`training` 18／`media` 15／`life` 12／`pressure` 11／`team` 10／`match` 10／
`transfer` 5／`body` 5／`crisis` 4。

```js
/** 當月訓練活動 → 月度事件卡 sub 的抽選傾向。沒列到的 sub 一律 1.0（不封鎖任何卡） */
const ACTIVITY_EVENT_BIAS = {
  fitness: { body: 2.5, life: 1.5 },      // 健身房：身體、作息
  scrim:   { team: 2.5, match: 1.5 },     // 團隊訓練賽：隊內關係、對抗
  vod:     { team: 1.5, pressure: 1.5 },  // 戰術覆盤：檢討會的摩擦與壓力
  soloq:   { media: 2.5, pressure: 1.5 }, // SOLO RANK：開台、炎上、天梯壓力
  study:   { match: 2.0, training: 1.5 }, // VOD 研究：對手情報、練習室日常
  rest:    { life: 2.5, media: 1.5 },     // 休息：生活、社群
};
```

配對邏輯與 S46 的錯位輪替同精神：六個活動各吃不同的 `sub` 組合，沒有兩個相同。
`transfer` 與 `crisis` **刻意不掛任何活動**——那兩條劇情軸該由狀態條件（`when`）驅動，
不該被「這個月練什麼」左右。

**2. 三條不能破的界線**

1. **只偏置隨機池，不碰條件卡。** 步驟 1 的 `condHits` 原封不動——§12.1 的
   「事件是對玩家狀態的回應」是條件卡存在的理由，它命中就該來。傾向只作用在
   步驟 2 與步驟 3 落到 `rng.pick(availableEvents(...))` 的**那兩處**。
2. **是加權不是開關。** 未列到的 `sub` 權重是 **1.0 不是 0**——每張卡永遠抽得到。
   這正是「變相鼓勵嘗試其他訓練」與「把內容鎖在單一路線」的分界線。
3. **不動防重與耗盡機制。** `availableEvents` 的耗盡／`recentEvents` 兩層先跑完，
   傾向只決定「在剩下的候選裡怎麼抽」。順序寫死：**過濾 → 加權 → 抽**。

**3. 實作**

- **`state.lastActivity`**：`resolveTraining` 開頭寫入 `state.lastActivity = activity.id`
  （休息也寫）。唯一真相來源，存檔帶著走。
- **加權抽選**：`rng.pick` 是均勻的。把 `drawTrainingCard` 裡那個區域性的加權 `pick`
  （`training.js:187-196`）抽出來變成 `Rng.prototype.weighted(items, weightOf)` 放進
  `src/core/rng.js`，`drawTrainingCard` 改用它——順手消掉一份重複實作。
  `eventTrigger` 的兩處改成：
  ```js
  rng.weighted(availableEvents(state, eligible),
    (ev) => ACTIVITY_EVENT_BIAS[state.lastActivity]?.[ev.sub] ?? 1)
  ```
- **條件語言也讀得到**（成本很低的額外收穫）：`ledger.js` 加 `lastActivityOf(state)`
  讀取端，`conditions.js` 的 `evalCond` switch 加
  `case 'lastAct': return lastActivityOf(state) === node[1];`。
  這樣卡片作者除了軟性傾向，還能寫死劇情連鎖（例如一張只在打完 SOLO RANK 之後
  才命中的開台事件），走的是既有的「寫在 `eventTrigger`、讀在 `ledger`」分層，不會成環。
  **這一項對之後的卡表重製特別有用**——新卡可以直接用 `lastAct` 寫條件。

**4. 內容編輯器（`tools/schema.js`）**

新增了一個條件節點，編輯器必須跟上——否則 `lastAct` 就是「引擎兌現得了、工具卻寫不
出來」，與 `SLOTS` 註解記載的那次脫節同型，只是方向相反。

- `COND_NODES`（`:136`）加 `'lastAct'`；`COND_NODE_LABELS` 加
  `lastAct: '上個月的訓練活動'`。
- `validateCond`（`:448`）要認得這個節點，值必須在**六項**選單活動之內。
  ⚠ 這與訓練卡的 activity 下拉**不是同一個集合**：訓練卡只標有卡池的**五項**，
  但 `lastAct` 要問得出「上個月是不是休息」。所以另外導一個
  ```js
  export const ACTIVITY_ALL = TRAINING_ACTIVITIES
    .filter((a) => a.menu !== false).map((a) => a.id);   // 六項，含 rest
  ```
  兩個集合共存但用途不同，在註解裡寫清楚——**不要為了「看起來一致」把它們併掉**。
- `SUB_TAGS`（`:61`）**不必動**：傾向表掛在既有的九個子標籤上，沒有新增分類。
  這也正是傾向表能撐過之後卡表重製的原因。

### 不要做

- **不改任何一張事件卡的文本、效果、`sub`、`when` 或權重**。卡表重製另案。
- **不補卡**（見下方「一個要先知道的內容限制」）。
- **不動 `slotHits` 時段過濾**、**不動 `SECOND_EVENT_CHANCE`**、
  **不動互斥（`excl`）檢查**。
- **不把加權套到 `condHits`** ——這是本站最容易犯的錯，也是唯一會破壞 §12.1 語意的改法。
- **不動訓練事件卡的抽選**（`drawTrainingCard` 只換成共用 helper，行為不變——
  要有測試守住「換 helper 前後同種子同結果」）。

## 一個要先知道的內容限制

`body` 只有 5 張、`crisis` 4 張。健身房把 `body` 加權 2.5 之後，那 5 張會很快被
`recentEvents` 的防重機制耗掉、退回全池，傾向就變得沒有感覺。

**本站不補卡**（卡表重製另案），但要在交接筆記寫明：傾向的實際手感受限於各 `sub`
的卡量，重製卡表時**每個被加權的 `sub` 建議至少 8 張**。

## 規則與不變式

- **條件卡不受偏置**（§12.1）：`condHits` 那條路上沒有任何權重。
- **傾向不封鎖**：未列到的 `sub` 權重恆為 1.0，每張卡都抽得到。
- **順序固定**：過濾（耗盡／防重）→ 加權 → 抽。
- **既有 `eventTrigger` 測試行為不變**：它們多半沒設 `state.lastActivity`，
  `?? 1` 的預設值必須讓它們維持均勻抽選。
- **`drawTrainingCard` 換 helper 不改行為**：同種子同結果。
- **編輯器寫得出來的 `lastAct` 值，引擎都認得**：`validateCond` 接受的集合
  == `TRAINING_ACTIVITIES` 的六個選單活動 id。

## 完成定義

- `npm test` 全綠。
- 新增測試：
  - **傾向生效**：同種子、`lastActivity = 'soloq'` 跑 200 次隨機池抽選，
    `sub === 'media'` 的佔比顯著高於 `lastActivity = 'fitness'` 的同一組。
  - **傾向不封鎖**：`lastActivity = 'soloq'` 跑夠多次，每個 `sub` 都至少出現一次。
  - **條件卡不受影響**：構造一張 `when` 必中的卡，切換 `lastActivity` 不改變它命中與否。
  - **`ACTIVITY_EVENT_BIAS` 的鍵全是合法活動 id、值的 `sub` 全在 `SUB_TAGS` 內**
    ——打錯字只會靜默退化成 1.0、不會報錯，這條擋掉它。
  - **`rng.weighted` 與原區域實作同結果**（同種子逐次比對）。
- **手動走查**：連續選 SOLO RANK 幾個月，開台／炎上類事件明顯變多但**沒有變成只有
  那一類**；換成健身房幾個月，身體與作息類跟著浮上來。
  ⚠ 這是本站**唯一真正的驗收標準**——數字對了但玩起來沒感覺，就把傾向係數從 2.5 往上調。
