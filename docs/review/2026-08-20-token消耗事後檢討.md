# 事後檢討：Token 消耗與文件膨脹（68 站完工後）

> 2026-08-20。範圍：V4 重建全 68 站的開發流程成本。程式與測試未動，本檔是提案，
> 未經拍板不施作。

---

## 一、量到的數字

全部由 repo 現況實測，不是估計：

- 程式碼 33,279 行（`src` `tests` `tools` `scripts`）。
- Markdown 95 檔、1,986,537 bytes。**文件體積約為程式碼的兩倍**。
- 文件變更 +56,242 行 / −611 行（刪除率 1.1%）；程式 +57,302 / −1,514。
  文件是純追加，寫進去就不再收斂。
- `docs/v4` 968,854 bytes，其中「交接筆記」421,998 bytes，占 **43%**。
- 跨檔重複：長度 40 字以上的句子，126 條各自出現在 2 個以上檔案，合計重複 299 次。
- 血緣（A／B 批）敘述散在 14 個 md 檔。

### 每站固定前置（`donggong` skill 第 2、3 步強制載入）

估算法：CJK 每字約 0.95 token，ASCII 每 4 字約 1 token。

- `docs/v4/README.md` 12,882
- `docs/v4/00b-穩定點快照.md` 5,301
- 目標站說明書（以 S49 為樣本）5,496
- `docs/v4/00-共通規則.md` 3,475
- `AGENTS.md` 3,094
- `CLAUDE.md` 1,284
- 小計 **31,532 token**

這還沒算：`ESPORT-DESIGN-V4.md` 指名章節（全書 75,737 token，單站通常吃 5,000–15,000）、
`WORKLOG.md` 前三條（約 3,300，但取用時整檔 100,153 token 在射程內）、程式碼、測試輸出、
審查包 diff。**實際開工前的一次性前置約 40,000–50,000 token。**

其中與站無關、68 站完全相同的部分是 26,036 token。乘 68 站 = **約 177 萬 token 的純重複載入**，
且這只算首輪；它留在上下文裡，之後每一輪都重送一次。

## 二、為什麼消耗這麼大：三個機制

不是「工作太多」，是三個可修的洩漏。

### 洩漏一：讀取單位是「檔案」，不是「切片」

- `README.md` 12,882 token，開工只需要其中一列狀態與前置站的一句話。載入率 2%。
- 收尾要改狀態表，於是同一份 12,882 token 再進上下文一次。
- 規格書 75,737 token，站說明書已經明確指名「必讀規格：V4 §5.3、§7、§20.2」，
  但沒有工具能按 § 切片，只能整檔或大段讀。
- `WORKLOG.md` 100,153 token，規則只要求讀前三條（3,300）。

**這是最大單筆浪費，也最好修**——規格書有 26 個 `##` 節、96 個 `###` 子節，錨已經在了。

### 洩漏二：同一事實抄四份

每站收尾寫進四個地方：站說明書交接筆記、`README.md` 狀態表與「現況」段、`WORKLOG.md`、
`CHANGELOG.md`。以 S49 抽樣，四檔各提及 3 至 9 次。四份都是散文，都會被後續 session 載入。

`AGENTS.md` 與 `.opencodereview/rule.json` 也是雙抄——`AGENTS.md` 第 7 條自己承認
「兩處同源，同一個 commit 一起改」。這正是專案「單一來源規則」禁止的事，規則沒有套用到規則自己身上。

### 洩漏三：文件沒有壽命，只有出生

- 交接筆記的讀者只有下一站。下一站做完就沒有人再讀，但它永久留在會被載入的檔案裡，
  已經長到 `docs/v4` 的 43%。
- `README.md` 的「現況」段是一段隨站數滾動增長的長句（4,690 bytes），每站追加，從不裁切。
  它記的內容狀態表已經有了。
- `CHANGELOG.md` 37 條、`WORKLOG.md` 102 條，都是月級以上的歷史，沒有封存線。

## 三、沒有意義、可以直接砍掉的消耗

依「省下的 token × 施作成本」排序：

1. **`README.md` 全檔載入**（省約 12,000 / 站）。開工只需要單站切片。
2. **`AGENTS.md` 的 path-scoped 工程規則**（省約 2,400 / 站）。條件語言、modifier 效果鍵、
   單一來源三節只在動到那些檔案時有用，卻每 session 全量注入，而且 `rule.json` 已有一份。
3. **`CLAUDE.md` 的 RTK 完整指令表**（省約 1,100 / 站）。核心規則只有三條
   （一律加 `rtk`、鏈中每段都加、要原始輸出用 `rtk proxy`），其餘是查得到的工具文件。
4. **規格書大段讀**（省約 5,000–10,000 / 站）。指名章節已經寫在說明書裡，缺的只是切片器。
5. **過期交接筆記**（省約 2,000 / 站，並縮小整個 `docs/v4`）。
6. **`README.md` 現況段**（省約 1,200 / 站）。狀態表已涵蓋，敘述是重複。
7. **審查包的未追蹤檔全文**（不定，尖峰很高）。`station-review.mjs` 對未追蹤檔附全文，
   新增大檔時會整檔進上下文。

合計每站可省 24,000–28,000 token，即固定前置的 **75% 以上**。

---

## 四、整套換掉還是改良

**改良，不要換。** 判斷理由：

貴的原因是上面三個洩漏，不是流程設計錯。流程實際交付的東西是有效的：68 站零回歸、
`npm test` 19,919 項、審查閘門是確定性的（委託模式不呼叫 LLM、不需 API key，本身幾乎不花錢）、
單一來源規則擋掉過四類實際 bug、S30／S36／S50 的「收斂站」模式證明可行。
整套換掉會把這些一起丟掉，換來的是重新踩一次同樣的坑。

流程層只有兩處值得動：

1. **加站規模上限**。「一 session 一站」保留，但說明書若估超過 400 行 diff 或跨 3 個以上模組，
   先拆站再開工。額度耗盡後的續接 session 要重付一次完整前置，是隱性成本最高的失敗模式。
2. **審查包瘦身**。未追蹤檔全文改為「超過 200 行只附前 100 行加結構摘要」。

## 五、方案

### 第一階段：前置瘦身（約 1 站工作量，立即見效）

1. `AGENTS.md` 砍到 40 行以內，只留不隨檔案變動的內容：收尾流程順序、commit 格式、
   版本編號規則、回覆風格、動工規則、rtk 三條。
2. 條件語言、modifier 效果鍵、單一來源三節從 `AGENTS.md` 移除，
   單一來源改放 `.opencodereview/rule.json`（本來就是 path-scoped 格式），
   由審查閘門與第二階段的簡報腳本按「本站要動的檔案」注入。消掉雙抄。
3. `CLAUDE.md` 砍到三條核心 rtk 規則。
4. 新增 `scripts/context-budget.mjs`：算出下一站前置的 token 估算，超過 10,000 就非零退出。
   預算從此可測，不靠感覺。

### 第二階段：切片載入（約 1 至 2 站工作量，收益最大）

5. 新增 `docs/v4/brief.mjs <站號>`，取代 `donggong` skill 第 2、3 步的六檔全讀。輸出單一份簡報：
   - 該站狀態表那一列，加各前置站交接筆記的「給下一站」小節；
   - `00-共通規則` 只輸出該站難度與分類相關的節；
   - `00b-穩定點快照` 只輸出基準座標與紅線數字；
   - 依說明書「必讀規格」欄位，按 § 從 `ESPORT-DESIGN-V4.md` 切出指名章節；
   - 依「要動的檔案」從 `rule.json` 帶出對應規則。
   目標：前置壓到 8,000 token 以下。
6. `ESPORT-DESIGN-V4.md` 拆成 `docs/spec/§NN-*.md`，主檔只留目錄與附錄決策紀錄。
   26 個 `##` 節就是天然切線。切片器與人工閱讀都受益。
7. 改寫 `.opencode/skill/donggong/SKILL.md`：第 2、3 步改為「跑 `brief.mjs`，讀它的輸出」。
   skill 本身也順勢縮短。

### 第三階段：文件收斂（約 1 站工作量）

8. 定四抄的單一來源：
   - 交接筆記是唯一的站級事實來源（下一站真的會讀它）；
   - `README.md` 狀態表只留機器可讀欄位，「現況」段刪除，需要時由腳本從狀態表生成；
   - `WORKLOG.md` 每條上限 15 行，只寫意圖與脈絡，實作細節指向交接筆記；
   - `CHANGELOG.md` 由 commit 訊息生成，不手寫。
9. 交接筆記加壽命規則：後續站完工後，把該站交接筆記壓成「給下一站的輸入」與「刻意沒做」
   兩節，其餘刪除（歷史在 git 裡）。
10. 封存線：`WORKLOG.md` 每 30 條切一份 `docs/archive/WORKLOG-YYYYMM.md`，主檔只留最近 10 條。

### 第四階段：血統追溯改成資料（約半站工作量）

11. A／B 批血緣現在散在 14 個 md 檔，敘述隨站數增長，但它的本質是**每個檔案的一個屬性**
    （A 批需淨室重寫／B 批原創／已淨室完成），不是每站要重講的故事。
    改成 `docs/lineage.json`：path glob 對應批次與淨室狀態，加一項測試檢查新增檔案已登記。
12. 散在各檔的血緣敘述刪除，只在 `docs/v4/02-血緣審計.md` 留「為什麼這樣處理」一段，
    淨室重寫做法寫成 20 行 checklist，不在每站重述。
    效果：血統追溯從隨站數放大的敘事，變成不隨站數成長的常數大小資料表。

## 六、驗收線

- 單站前置 token 8,000 以下（現況 31,532），由 `context-budget.mjs` 量。
- `docs/v4` 壓到 400,000 bytes 以下（現況 968,854）。
- 跨檔重複句從 126 條降到 30 條以下。
- 一站一句事實只寫在一個檔案裡；重複由腳本生成，不由人手抄。
- `npm test` 19,919 項維持全綠——文件收斂不得動到程式與測試。

## 七、刻意沒做

- 沒有動任何程式、測試、規格內容。本檔是提案。
- 沒有改 OCR 審查閘門的判準（critical／high 擋 commit 的規則有效，保留）。
- 沒有提議放棄「一 session 一站」——它是額度爆掉時的止血點，只加規模上限。
- 沒有提議換掉 rtk。rtk 管的是 CLI 輸出，本檔談的是文件載入，兩者不重疊，
  且 rtk 已有 `gain --history` 在量自己的節省；缺的是文件側的同類量測，見第一階段第 4 項。
