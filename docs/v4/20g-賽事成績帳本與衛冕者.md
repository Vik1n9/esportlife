## 為什麼做這件事

起點是 `20c` 要接線的 `UNIQUE_TRAITS` 三條死資料，其中 `torch_bearer`（火炬手）的
授予條件是**「世界賽淘汰現任世界冠軍——史實成就：世代交替的那一手」**。查核發現
這條**接不上**，因為遊戲裡根本沒有「現任世界冠軍」這個東西：

**一、對手沒有身分，只有強度。** `worlds.js:32` 的 `intlOpponent()` 全文就是一個數字：

```js
function intlOpponent(state, step, rng) {
  const base = Math.max(LEAGUES[state.league]?.par ?? 66, 74);
  return opponentStrength(base + step + bonus(state, 'worldsRoll') * -0.15 + rng.gauss(1.6));
}
```

八強／四強／決賽三輪只差一個 `step`（6.25／9.5／12.5），`oppNote` 是寫死的字串
（`'對手是各賽區的一號種子。'`）。**沒有隊名、沒有賽區、沒有 id。**
`runSeriesEvent` 收到的只有 `oppRating`（數字）與 `seed`。

**二、玩家沒奪冠的年份，遊戲不知道誰奪冠。** `wonWorldsThisYear`／`worldsWins`
只記玩家自己，全 `src/` 沒有任何 NPC 冠軍登記表。唯一提到「衛冕王」的地方是
`quests.js:50` 的任務卡敘事文字——**純風味，底下沒有機制**。

### 使用者在 PR #16 提出的擴充

> 將變數訂為 NPC 和玩家共用，功能為追溯上一屆相同賽事的戰績（八強、亞軍、冠軍、
> 四強等），當屆賽事結束則更新。目的：提供特質和事件更多可用條件；生涯榮譽好記錄；
> 隔屆事件可抓這個變數改文本。

查核後確認這個設計**順手根治了 A3／N3**（名次鍵入帳之後就不必解析文字了），
因此拆成兩半：**帳本那半移進 S20c**（它是 A3／N3 的根治手段），
**身分與衛冕者那半留在本站**。

### 為什麼排在 S20c 與 S20d 之間

- **要在 S20c 之後**：`unique` store 與名次鍵入帳都由 S20c 建好，本站才有東西可接。
- **要在 S20d 之前**：多一個「比常規對手更強」的衛冕冠軍會**壓低世界賽勝率**，
  而世界冠軍人均是有基準的數字（`strength.js` 的 `OPPONENT_SUPPORT` 註解記載
  640 段實測 **0.128**）。排在 S20d 之前，讓那一站的校準掃描**一次吸收**本站與
  起點改動的合併效果，不必校準兩輪。

### 庚組相容性（本站的設計約束）

S28「隊友與戰隊整合（NPC 池、縮寫顯示）」會帶進**真的 NPC 戰隊**。本站建的身分層
必須是那時候**替換內容、不替換結構**：登記表欄位與對手標記的管線留著，
只把「合成的冠軍」換成真的戰隊參照。**不要**做成只給 `torch_bearer` 用的一次性旗標。

## 範圍

### 要做

**1. 冠軍登記表（NPC 與玩家共用）**

`state.titleHistory`（對齊既有的 `teamHistory` 命名慣例）：

```js
[{ year, event: 'worlds', finish: 'champion', team, region, isPlayer }]
```

玩家奪冠與 NPC 奪冠**寫進同一張表**——這就是使用者要的「共用變數」。

- 玩家奪冠 → `isPlayer: true`，`team` 是玩家的隊伍
- 玩家沒奪冠或沒參賽 → 抽一個合成冠軍：**賽區依世界賽席位數加權**
  （`worldsSlotsOf`，席位多的賽區奪冠機率高，現成資料），隊名走
  `teamNamesOf(region, eraKey)`（`roster.js:37` 已在用，自動吃時代改名，
  **零新內容**，順帶避開 `20b` 的 N18 那種「2016 年的台北暗殺星」跨時代錯誤）
- 遊戲第一年沒有衛冕冠軍 → 表是空的，本年不標記

⚠ 存檔要帶得動。`SAVE_VERSION` 已由 S20c 升到 20——本站若獨立發版要再升一次，
照 `state.js:19-29` 的體例加註解行。state 必須維持純 JSON（`state.js:1-6`），
所以用普通物件陣列，**不要用 `Map`**。

**2. 查詢層（讓特質與事件用得到）**

| 查詢 | 讀什麼 | 回什麼 |
| --- | --- | --- |
| `lastFinish(state, event)` | `milestones`（S20c 已入帳的 `finish`） | 上屆同賽事名次鍵；**不儲存，導出即可** |
| `reigningChampion(state, event)` | `titleHistory` | 上屆冠軍的 `{team, region, isPlayer}` |

⚠ **兩處註冊表要同步**：新謂詞要同時加進 `conditions.js:49` 的 `QUERIES`
與 `tools/schema.js:134` 的 `PREDICATES`（`schema.js:131` 的註解明寫這件事，
`AGENTS.md` 條件語言規則也明文要求）。

**2b. 統一條件語言：退役 `whenHits`，事件卡改吃 `evalCond`**

> **2026-08-15 已拍板**（PR #16）：使用者裁定「兩者規格上必須對齊」，
> 規則已寫進 `AGENTS.md` 的〈條件語言規則〉。**本站執行這個遷移。**

現況是兩套語言：任務卡走 `evalCond`／`QUERIES`（`conditions.js`，
s-expression、謂詞可擴充、讀查詢層），事件卡走 `whenHits`
（`eventTrigger.js:94`，只支援 stage／minAge／maxAge／attr／trait／mental，
且 `trait` 只讀 common 階、語意與文件相反）。同一個條件在兩邊要寫兩次，
而且新的 `lastFinish`／`reigningChampion` 謂詞在 `whenHits` 那邊**寫不出來**。

做法：

1. `eventTrigger.js` 的第 1 步條件命中改呼叫 `evalCond`，`whenHits` 移除。
2. 卡片的 `when` 欄位改成 s-expression（與任務卡的 `trigger` 同一種形狀）。
3. `tools/schema.js` 的事件卡 `when` 編輯器改用既有的**條件式積木**
   （S18b 已經為任務卡做好 `type: 'cond'` 的積木／原始 JSON 雙模式，直接複用）。
4. 遷移後 `whenHits` 的三個缺陷（S20c 的 N6：AND／OR 語意相反、只讀 common 階、
   文件範例 `godhand` 是 epic 永不觸發）**自動消失**——`evalCond` 的
   `['has', 階, 鍵]` 四階都支援。

⚠ **零內容成本**：實測 86 張卡 `when` **0 張**，沒有任何既有內容要改寫。
這是做這個遷移最便宜的時間點——S20f 一旦開始寫條件就不便宜了。

⚠ **`slot` 不動**：時段過濾是觸發演算法的步驟 0，不是條件（`AGENTS.md` 明文）。

**3. 對手身分管線**

`runSeriesEvent` 的 opts 增加可選的對手標記（`oppTag`／`oppTitle`），
`worlds.js` 的 `knockout()` 在建立每一輪的 series 時決定要不要掛。

⚠ **只做「掛得上標記」這件事，不要順手把對手改成完整實體。** 完整實體是 S28。

**4. 衛冕冠軍在不在玩家的賽路上**

不是每年都會碰到。要一個明確的規則（本站定案並寫進交接筆記），建議：
衛冕冠軍佔一個淘汰賽席位，玩家與他相遇的機率隨輪次加深而上升
（八強 < 四強 < 決賽）——與「兩支強隊通常在後段相遇」的直覺一致。

邊界情形要處理：

| 情形 | 處理 |
| --- | --- |
| 玩家自己就是衛冕冠軍 | 不標記（不能淘汰自己）。可考慮改為「所有對手都想扳倒你」的敘事 |
| 第一年（無衛冕冠軍） | 不標記 |
| 衛冕冠軍該年沒晉級世界賽 | 不標記（合成冠軍也要過席位檢查） |
| 小組賽／Swiss 遇到 | 本站定案要不要算（**建議只認淘汰賽 BO5**） |

**5. 衛冕冠軍的強度加成**

他是冠軍，該比同輪的一般對手強。加成幅度由本站定，並**量出它對世界賽勝率與
世界冠軍人均的影響**——這個數字要交給 S20d。

**6. `torch_bearer` 授予**

玩家在世界賽**淘汰賽**贏下標記為衛冕冠軍的那一組 BO5 → 發 `torch_bearer`
（`unique` 階，走 S20c 建好的發放形狀，**不是** `unlockTrait`）。

**7. 敘事**

對上衛冕冠軍要看得出來——`oppNote` 現在是寫死字串（`seriesEvent.js:68` 是唯一
消費點），改成能帶隊名／「衛冕冠軍」標籤。贏下那一組要有 beat
（世代交替是這條特質的主題）。

⚠ 卡片文本的 `{變數}` 填空機制是 [S20h](20h-卡片文本變數.md) 的範圍。
本站只做**引擎產生的敘事字串**（`oppNote` 與 beat），不動卡片資料檔。

### 不要做

- **不要把對手改成完整 NPC 實體**（S28 的範圍）。本站只建「身分標記」這一層。
- **不要在這一站重跑 160 段校準**——量出影響量交給 S20d，本站不調門檻。
- **不要為衛冕冠軍新增戰隊名單資料**。用 `teamNamesOf` 既有的名單。
- **不要動卡片資料檔的文本**（S20h）。
- 不要動 MSI 的衛冕邏輯（§18.2 的 `torch_bearer` 條件只講世界賽）——
  但登記表的 `event` 欄位要能容納 MSI，未來補得上。

## 規則與不變式

- **`torch_bearer` 要有可達性測試**——構造狀態直接驗，不靠 160 段碰運氣
  （`20b` 的教訓：只驗 schema 不驗遊戲內取得，全綠也抓不到死資料）。
- **衛冕冠軍每年必定有人**（除了第一年）：登記不得有空窗，否則過幾年就沒人可淘汰。
- **玩家奪冠後下一年自己是衛冕冠軍**，且該年不會把自己標成對手。
- **合成冠軍的隊名必須是該年代真實存在的隊名**（走 `teamNamesOf`）。
- **登記表的形狀對玩家與 NPC 一致**——這是「共用變數」的定義，也是 S28 能換內容
  不換結構的前提。
- **條件語言只剩一套**：遷移後全 `src/` 不得再有第二個條件求值器
  （`AGENTS.md` 條件語言規則）。`whenHits` 要真的刪掉，不是留著沒人叫。
- **新謂詞兩張註冊表都要有**（`conditions.js` 的 `QUERIES` ＋
  `tools/schema.js` 的 `PREDICATES`）——補一組測試斷言兩邊的鍵集合相同。
- 存檔往返帶得動 `titleHistory`。
- `npm test` 全綠。

## 交接筆記

### 一、修前紅燈（守得住的前提）

- 本站補的最重要測試是「兩張註冊表鍵集合相同」（`tests/kernel/conditions.mjs`）：
  斷言 `conditions.js` 的 `QUERIES` 與 `tools/schema.js` 的 `PREDICATES` 鍵集合相等。
  **修前它是紅的**——S20c 把 `careerGames`／`awardsThisYear` 加進 `QUERIES` 卻漏在
  `PREDICATES` 外面（跟 AGENTS.md 點名的「unique 階脫節」同一種失敗模式）。紅燈輸出：

  ```
  ✗ QUERIES 每一鍵都在 PREDICATES 內 — awardsThisYear
  ```

  遷移 `whenHits` → `evalCond` 之前，事件卡條件若要讀屬性（舊 `when.attr`），`tec` 等
  鍵也不在謂詞表——所以一併把六大屬性鍵補進兩張註冊表（同一套「缺欄位回 0」寫法）。

### 二、設計定案值（S20d／S20f／S20h 要對齊）

| 項 | 定案 | 出處 |
| --- | --- | --- |
| 相遇機率 | 八強 15%／四強 30%／決賽 60%（餵 `rng.chance` 的百分比） | `engine/champion.js` `CHAMPION_ENCOUNTER` |
| 衛冕者強度加成 | **+4 點**（0–100 刻度，加在 `intlOpponent` 的階梯 step 上） | `engine/champion.js` `CHAMPION_BONUS` |
| `torch_bearer` 授予 | **事件即時授予**（`grantUnique`，非 `unlockTrait`、非 `grantWhen`），`grantWhen` 維持 null | `phases/worlds.js` `knockout()` |
| 事件卡條件語言 | **改吃 `evalCond`**，`whenHits` 已刪；`when` 欄位是 s-expression | `engine/eventTrigger.js` |

### 三、實測結論（200 段生涯＝40 種子 × 5 位置，first 策略，focus/spread 各半）

- **`torch_bearer` 取得率 8/200 = 4.0%**——是可達的中高難度頂端目標，不是死資料。
- **世界冠軍人均變動量**（A/B，同種子同策略）：
  - 無衛冕者機制（encounter 0%、bonus 0）：**0.055**（11 座／200 段）
  - 本站上路：**0.035**（7 座／200 段）
  - 差 **−0.02／段（−36%，11→7 座）**。⚠ 樣本小（200 段只有 7–11 座），
    這個數字交給 **S20d** 的校準掃描做母體級的再確認，本站不調任何門檻。
  - ⚠ `strength.js` 註解記的基準 0.128 是 S11/S12 年代 640 段量的，早已被 S15b／
    S16／S18–S19 動過——**現在的「衛冕者上路前」基準是 0.055，不是 0.128**。S20d
    校準請以 0.055 當起點，別拿 0.128 對。
- **登記無空窗**：`titleHistory` 逐年連續（檢查 1747 個「次年」接點，空窗 0）。
  復健年（`skipSeason`）原本會跳過世界賽、留空窗，已修：復健年照樣登記一個 NPC 冠軍
  （世界賽照常舉行，只是玩家沒參賽）。
- 世界賽「世界冠軍人均」本身遠低於 0.128，是因為歷站疊加後的現況，非本站引入。

### 四、庚組 S28 接手時要換掉的行

`engine/champion.js` 的 `drawChampion()`（`rng.pick(teamNamesOf(r, eraOf(state.year).home))`
那一行）——S28 帶進真 NPC 戰隊池後，把「抽一個合成隊名」換成「參照真的戰隊實體」。
**其餘不動**：`titleHistory` 欄位、`reigningChampion`／`challengableChampion` 查詢、
`knockout()` 的標記管線原封不動——換內容不換結構。

### 五、留給後面的注意事項

- **事件卡 `when` 現在是 s-expression**（S20f 寫內容時照 §12.1 條件式語法寫，與任務卡
  `trigger` 同形狀）。舊 `whenHits` 的 `stage` 條件已由步驟 0 的時段過濾（slot）承接，
  不需再列；`attr` 範圍條件用 `['stat', 'tec', 'gte', 70]` 表達（六屬性已進謂詞表）。
- **`titleHistory` 的 `event` 欄位容納 MSI**（未來補 MSI 衛冕者只要在 `msi.js` 也呼叫
  `registerChampion` 同款寫入即可），本站照說明書**沒動 MSI**。
