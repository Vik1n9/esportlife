# S20g · 衛冕者追蹤與對手身分

狀態：未開始
前置：S20c
預估：1 session
推理難度：高
建議模型：Opus 5（`claude-opus-5`）
理由：這一站要在「對手一直是純數字」的引擎裡插進第一個**對手身分**概念，而且要插得
讓庚組（S28 真 NPC 戰隊池）接得上、不必重寫。同時它會動世界賽的勝率分布
（多一個變強的對手），所以要與 S20d 的校準掃描接在一起。降級的風險是把身分做成
只給 `torch_bearer` 用的一次性旗標，庚組進場時整段丟掉。

> ⚠ **編號非字母序**：本站是 PR #16 審查後追加的，排在 S20c 與 S20d 之間
> （見下方「為什麼排在這裡」）。依賴關係以本表的「前置」欄為準，不以字母順序為準。

## 為什麼做這件事

`20c` 要把 `UNIQUE_TRAITS` 三條死資料接線，其中 `torch_bearer`（火炬手）的授予條件是
**「世界賽淘汰現任世界冠軍——史實成就：世代交替的那一手」**。查核發現這條**接不上**，
因為遊戲裡根本沒有「現任世界冠軍」這個東西：

**一、對手沒有身分，只有強度**

`worlds.js:32` 的 `intlOpponent()` 全文就是一個數字：

```js
function intlOpponent(state, step, rng) {
  const base = Math.max(LEAGUES[state.league]?.par ?? 66, 74);
  return opponentStrength(base + step + bonus(state, 'worldsRoll') * -0.15 + rng.gauss(1.6));
}
```

八強／四強／決賽三輪只差一個 `step`（6.25／9.5／12.5），`oppNote` 是寫死的字串
（`'對手是各賽區的一號種子。'`）。**沒有隊名、沒有賽區、沒有 id。**

**二、玩家沒奪冠的年份，遊戲不知道誰奪冠**

`state.wonWorldsThisYear`／`worldsWins` 只記玩家自己。全 `src/` 沒有任何 NPC 冠軍
登記表。唯一提到「衛冕王」的地方是 `quests.js:50` 的任務卡敘事文字——**純風味，
底下沒有機制**。

所以這一站不是「加一個欄位」，是**建立對手身分層**：先有「誰是衛冕冠軍」，
才談得上「淘汰他」。

### 為什麼排在 S20c 與 S20d 之間

- **要在 S20c 之後**：`unique` 階的 store 與授予機制由 S20c 建好，本站只補
  `torch_bearer` 這一條的觸發點。
- **要在 S20d 之前**：多一個「比常規對手更強」的衛冕冠軍會**壓低世界賽勝率**，
  而世界冠軍人均是有基準的數字（`strength.js` 的 `OPPONENT_SUPPORT` 註解記載
  640 段實測 **0.128**）。排在 S20d 之前，讓那一站的校準掃描**一次吸收**本站與
  起點改動的合併效果，不必校準兩輪。

### 庚組相容性（本站的設計約束）

S28「隊友與戰隊整合（NPC 池、縮寫顯示）」會帶進**真的 NPC 戰隊**。本站建的身分層
必須是那時候**替換內容、不替換結構**：`reigningChampion` 欄位與對手標記的管線留著，
只把「合成的冠軍」換成真的戰隊參照。**不要**做成只給 `torch_bearer` 用的一次性旗標。

## 範圍

### 要做

**1. 衛冕冠軍登記（state 層）**

每年世界賽結束後決定「下一年的衛冕冠軍是誰」，存成一個滾動欄位
（例如 `state.reigningChampion = { year, team, region, isPlayer }`）。

- 玩家奪冠 → 衛冕冠軍是玩家的隊伍（`isPlayer: true`）
- 玩家沒奪冠或沒參賽 → 抽一個合成冠軍：**賽區依世界賽席位數加權**
  （`worldsSlotsOf`，席位多的賽區奪冠機率高，這是現成資料），
  隊名用既有的 `teamNamesOf(region, eraKey)`（`roster.js:37` 已在用，
  自動吃時代改名，不必新增內容）
- 遊戲第一年沒有衛冕冠軍 → `null`，本年不標記

⚠ 存檔要帶得動這個欄位。`SAVE_VERSION` 已由 S20c 升到 20——**本站若在 S20c 之後
獨立發版，要再升一次**（20 → 21），照 `state.js:19-29` 的體例加註解行。

**2. 對手身分管線（引擎層）**

`runSeriesEvent` 的 opts 增加一個可選的對手標記（例如 `oppTag`／`oppId`），
`worlds.js` 的 `knockout()` 在建立每一輪的 series 時決定要不要掛。

⚠ **只做「掛得上標記」這件事，不要順手把對手改成完整實體。** 完整實體是 S28。

**3. 衛冕冠軍在不在玩家的賽路上**

不是每年都會碰到。要一個明確的規則（本站定案並寫進交接筆記），建議：
衛冕冠軍佔一個淘汰賽席位，玩家與他相遇的機率隨輪次加深而上升
（八強 < 四強 < 決賽）——這與「兩支強隊通常在後段相遇」的直覺一致。

邊界情形要處理：

| 情形 | 處理 |
| --- | --- |
| 玩家自己就是衛冕冠軍 | 不標記（不能淘汰自己）。可考慮改為「所有對手都想扳倒你」的敘事 |
| 第一年（無衛冕冠軍） | 不標記 |
| 衛冕冠軍該年沒晉級世界賽 | 不標記（合成冠軍也要過席位檢查） |
| 玩家在小組賽／Swiss 遇到 | 本站定案要不要算（建議只認淘汰賽 BO5） |

**4. 衛冕冠軍的強度加成**

他是冠軍，該比同輪的一般對手強。加成幅度由本站定，並記錄它對世界賽勝率的影響量
——**這個數字要交給 S20d**。

**5. `torch_bearer` 授予**

玩家在世界賽**淘汰賽**贏下標記為衛冕冠軍的那一組 BO5 → 發 `torch_bearer`
（`unique` 階，走 S20c 建好的發放形狀，不是 `unlockTrait`）。

**6. 敘事**

對上衛冕冠軍要看得出來——`oppNote` 現在是寫死字串，改成能帶隊名／「衛冕冠軍」
標籤。贏下那一組要有 beat（世代交替是這條特質的主題）。

### 不要做

- **不要把對手改成完整 NPC 實體**（S28 的範圍）。本站只建「身分標記」這一層。
- **不要在這一站重跑 160 段校準**——量出影響量交給 S20d，本站不調門檻。
- **不要為衛冕冠軍新增戰隊名單資料**。用 `teamNamesOf` 既有的名單。
- 不要動 MSI（§18.2 的條件只講世界賽）。

## 規則與不變式

- **`torch_bearer` 要有可達性測試**——構造狀態直接驗，不靠 160 段碰運氣
  （`20b` 的教訓：只驗 schema 不驗遊戲內取得，全綠也抓不到死資料）。
- **衛冕冠軍每年必定有人**（除了第一年）：登記不得有空窗，否則過幾年就沒人可淘汰。
- **玩家奪冠後下一年自己是衛冕冠軍**，且該年不會把自己標成對手。
- **合成冠軍的隊名必須是該年代真實存在的隊名**（走 `teamNamesOf`，
  不得出現 `20b` 的 N18 那種「2016 年的台北暗殺星」跨時代錯誤）。
- 存檔往返帶得動 `reigningChampion`。
- `npm test` 全綠。
